# Prescribe harness gates, publish agent scores

Leading labs define an agent score as a model plus the harness around it, and they tell builders to grade environment outcomes, read traces, and run deterministic checks on every change. The harness is the loop, tools, gates, memory, and prompts, with the weights held fixed. What those labs report from their own systems is a launch-time measurement of the pair: a named scaffold, a step or token budget, hidden tests or an official environment script, and an average over several trials. When a study holds the model still and changes the harness, the result moves by more than ordinary leaderboard noise. Anthropic measured a **6 point** swing on Terminal-Bench 2.0 from machine limits alone, a **12.2 point** lift from adding subagents on an internal retrieval set, and a jump from **42% to 95%** on CORE-Bench after grader bugs and a less constrained scaffold. Google research, weights fixed, reports harness edits of up to **11.8 points**, and a cross-harness study finds full-credit rates that shift by **9.1 to 13.5 points** for the same model. The standing release table still prints one number per model. The merge gate described in the essays, a suite that fails a harness change before it ships, is the practice the system cards leave unpublished.

## A published agent score already includes the harness

By early 2026 the labs use one object for the software around the model and a second object for the runner that grades it. Anthropic’s January 2026 eval essay states the split directly: an agent harness, also called a scaffold, “processes inputs, orchestrates tool calls, and returns results,” and “when we evaluate an agent, we’re evaluating the harness and the model working together.” The evaluation harness is the other piece of software: it supplies instructions and tools, runs tasks, records the transcript, grades, and aggregates. The outcome they want graded is environment state, a reservation row in SQL, for example, rather than the agent’s claim that it booked the flight ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). OpenAI’s January 2026 Codex post uses harness for the product loop: query the model, execute the tool call, append the tool output, and repeat until the model emits an assistant message. The prompt is assembled from instructions, tools, and input, including model-specific instruction files ([Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)). A cookbook page calls the harness “the full contract around the model, including instructions, tools, routing, output requirements, and validation checks” ([Agent improvement loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)). Google’s Harness² README, marked as research code rather than a supported product, defines a harness as prompts, tools, memory, skills, orchestration, and the rest of the system around fixed weights, and lists eight editable parts: system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, and plugins ([Harness²](https://github.com/google-research/harness2)). A DeepMind paper puts the same idea as plumbing: an agent is “a specific LLM and a harness,” and the harness can be code that calls the model and rejects unacceptable actions ([AutoHarness](https://arxiv.org/html/2603.03329)). Microsoft’s agent-framework docs describe the harness as the runtime that drives model and tool calls, holds conversation state, applies approval policies, and can compact context, track todos, and bound a loop ([Agent Harness](https://learn.microsoft.com/en-us/agent-framework/concepts/harness)). The UK AI Security Institute’s engineering playbook makes the synonym explicit: solver, scaffold, and harness are one entry, “the structure put in place to let the model attempt the task,” and the same samples can be run under different solvers so the wrapper is the thing that changes ([AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)).

That vocabulary is already visible in older benchmark write-ups, which is why a model-only reading of those scores was never available. In January 2025 Anthropic described SWE-bench as a test of model plus scaffolding, the prompts, the parser, and the loop, and reported one scaffold, a prompt plus Bash plus a string-replace editor, at **49%**, **33%**, and **22%** for three Claude models on SWE-bench Verified ([Raising the bar on SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet)). The Opus 4.6 system card later reproduced GPT-5.2-Codex at **57.5%** on the Terminus-2 harness and **64.7%** on OpenAI’s Codex CLI harness across **890 trials**, and it flags an earlier GPT-5.1-Codex-Max figure as a different harness that Anthropic could not reproduce ([Claude Opus 4.6 system card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)). OpenAI’s February 2025 deep-research card reports SWE-bench under two scaffolds, Agentless for earlier models and an internal iterative editing scaffold for o3-mini and deep research, and it calls preparedness numbers a lower bound because a different scaffold, a longer rollout, or a different prompt could elicit more ([Deep research system card](https://cdn.openai.com/deep-research-system-card.pdf)). Google’s November 2026 Multimodal Knowledge Agent benchmark does the complementary experiment: every model runs in one open-source harness, Stirrup, with the same tools, sandbox, and turn budget, so the model is what the table is allowed to credit ([MKA benchmark](https://blog.google/innovation-and-ai/models-and-research/gemini-models/multimodal-knowledge-agent-benchmark/)). The comparable unit in every one of these reports is model, scaffold, tool access, and budget. A leaderboard cell that omits the scaffold is a joint score with the harness left unnamed.

## Environment tests are the lab rule, and tool traces are the vendor rule

The coding labs that publish agent numbers tell builders to grade the world the agent changed. Anthropic’s practical line for coding evals is unit tests for correctness and an LLM rubric for quality, with extra graders only when needed. SWE-bench Verified passes only if the patch fixes the failing tests and leaves the existing tests green. The essay warns that requiring a specific tool-call sequence makes brittle tests, because agents find valid paths the designer did not list, so the grade should attach to the product of the run. Transcript checks stay in the menu for tool behavior, turn caps, tokens, and latency. Capability suites should start at a low pass rate. Regression suites should sit near **100%** and run continuously. A task that fails on every one of 100 trials is, in their words, most often a broken task ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). Their customer-facing eval skill is stricter about the same idea: the primary grader reads end state, a transcript check is for process guardrails such as “asked before deleting,” the model under test should stay off the judge seat, and a case that passes only on a retry stays a fail unless someone decides otherwise ([build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)). The tools essay adds a held-out set when descriptions are being hill-climbed, and it allows an expected-tool check only as an optional signal of whether the model grasped the tool, with an explicit warning against overfitting a path ([Writing effective tools for agents](https://www.anthropic.com/research/writing-tools-for-agents)).

OpenAI’s published coding rule matches that outcome standard and then withdraws the benchmark that made it famous. The agent sees the issue and the repo. The tests stay hidden. A patch passes only when both the fail-to-pass and the pass-to-pass suites pass. On 23 February 2026 OpenAI said it had stopped reporting SWE-bench Verified. An audit of **138** problems, a **27.6%** slice of tasks models often failed, found material test or description issues in **59.4%**. Of the audited tasks, **35.5%** had tests that enforce implementation details, and **18.8%** had tests for behavior absent from the problem statement. The recommended replacement on that page is SWE-bench Pro, with a note that some Pro contamination existed and was rarer, and that no model produced a complete verbatim gold patch ([Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). For builders, the platform docs split three questions that a single final-answer grade would collapse: whether the agent called the right tool, whether the arguments were right, and whether the user-facing answer was right. Deterministic checks come first. A judge, named on the best-practices page as `gpt-6-astra`, is scaled after it ranks human-labeled answers in the same order. The worked workflow says to run evals on every prompt, model, and tool change ([Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). The realtime cookbook adds the regression shape: a frozen set of hard cases, a holdout that stays untouched, mocked tool outputs, and a pinned user-simulator prompt ([Realtime eval guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)).

Google’s customer stack, Microsoft’s, and LangSmith’s make the trace the assertable object, which is a different pass rule aimed at the same harness. Vertex scores a predicted tool sequence against a reference with exact match, in-order match that allows extra calls, any-order match, precision, recall, and single-tool presence. ADK’s default, if the caller sets nothing, is **tool-trajectory average score at 1.0** and **ROUGE-1 response match at 0.8**. A judged rubric is a majority vote, default **five** samples of `gemini-2.5-flash`, because one judge call is treated as unreliable. Token, latency, and call-count metrics are informational and are rejected as failure conditions. The docs tell builders to put the two deterministic scores in CI, and they describe a conformance test that can block a pull request when expected behavior changes ([ADK evaluation](https://adk.dev/evaluate/), [ADK criteria](https://adk.dev/evaluate/criteria/), [ADK eval config](https://github.com/google/adk-python/blob/main/docs/guides/evaluation/eval_config/index.md)). A November 2025 Cloud post adds a third pillar, trust, covering prompt injection and fairness, and it says the suite should fail the build when a score drops under a threshold ([A methodical approach to agent evaluation](https://cloud.google.com/blog/topics/developers-practitioners/a-methodical-approach-to-agent-evaluation)). Microsoft’s local evaluator checks keywords, tool names with extras allowed, and argument subsets, and it is described as the tool for CI smoke tests. Cloud judges add tool-call accuracy automatically when tool definitions are present, and the Foundry guidance says to pin the dataset, the deployment, the evaluator, and the rubric, then fail CI on a regression ([Microsoft agent evaluation](https://learn.microsoft.com/en-us/agent-framework/agents/evaluation), [Foundry evaluation](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/evaluation/microsoft-foundry)). LangSmith’s trajectory match is exact, unordered, subset, or superset. Strict mode still allows the message text to differ. The default tool comparison requires the same arguments. An LLM judge is the alternative when the question is whether the path was reasonable ([LangSmith trajectory evals](https://docs.langchain.com/langsmith/trajectory-evals)).

The measured comparison of those two grader families comes from Meta, not from a product launch. The Agents Research Environments verifier scores write actions against an oracle graph and ignores reads, on the claim that many read strategies can reach the same writes. A hard check demands exact parameters. A soft check asks a model whether the remaining arguments are equivalent. Every oracle write must match, causality must already hold, and timing must fall inside a tolerance, **5 seconds** before and **20 seconds** after in the published example. On **450** human-labeled trajectories, with Llama 3.3 70B Instruct as the judge, an in-context model reading the whole trajectory agreed with humans at **0.72** and had precision **0.53**. The scripted-plus-soft verifier agreed at **0.98**, with precision **0.99** and recall **0.95**. The paper says the in-context judge accepts trajectories too readily ([ARE](https://arxiv.org/html/2509.17158), [ARE judge system](https://facebookresearch.github.io/meta-agents-research-environments/api_reference/validation.html)). That result supports a specific stack. Hidden environment checks, or a short list of mandatory side effects, decide correctness. A model that rereads the whole transcript is the weaker instrument, useful where the question is taste, and only after a human comparison like the one Meta published. Exact trajectory match, which is ADK’s default, is the version of this stack most likely to freeze one path. Anthropic’s coding advice is the version that refuses to freeze the path. Google’s own September 2026 coding-agent post sits closer to Anthropic on this point: assert a tool call or a file change for a simple task, and for a complex task use an outcome check, because a rigid sequence is the wrong oracle ([Anatomy of harness engineering](https://developers.googleblog.com/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/)).

## Fixed-weight edits move scores by about 6 to 13 points

The experiments that isolate the harness are fewer than the launch tables, and they are the ones that answer whether the wrapper is worth a separate eval. Anthropic’s February 2026 infrastructure study held the Claude model, the harness, and the Terminal-Bench 2.0 task set fixed, and varied only the machine. Infrastructure errors fell from **5.8%** under a strict 1× cap to **0.5%** uncapped. From 1× to 3×, success stayed inside noise (**p = 0.40**) while the error rate fell to **2.1%** (**p < 0.001**). From 3× to uncapped, errors fell another **1.6 points** and success rose almost **4 points**. Uncapped versus 1× was **+6 points** (**p < 0.01**). A SWE-bench crossover, **227** problems and **10** samples, with RAM up to 5×, moved only **1.54 points**. Their published skepticism line is that leaderboard gaps under about **3 points** stay unresolved until the configuration matches, because a binomial interval on these sets already spans **1 to 2 points** and infrastructure sits on top. They also report an unquantified time-of-day effect from API latency ([Quantifying infrastructure noise](https://www.anthropic.com/research/infrastructure-noise)). The system cards show the policy changing under the same benchmark. Opus 4.5’s card describes low limits that introduced flakiness of up to **13%**, mostly containers running out of memory, then a 2× bump that cut infrastructure errors below **1%**, with Terminal-Bench at **59.27% ± 1.34%** on **1,335** trials at a 128k thinking budget. Opus 4.6’s card uses a 1× guarantee and a 3× kill ceiling, all **89** tasks, **15** times each, spread over three batches, and prints **65.4%** at max effort ([Claude Opus 4.5 system card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf), [Claude Opus 4.6 system card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)).

Tool, memory, and multi-agent wrappers move the number by at least as much, with weaker statistics on some of the comparisons. On BrowseComp-Plus, which the Opus 4.5 card describes as an evaluation of memory and context tools, tool-result clearing scored **67.59%** and clearing plus a memory tool scored **72.89%**, in a setup whose figure is labeled as single runs. The same card’s internal retrieval benchmark reports Opus 4.5 with Haiku 4.5 subagents at **87.0%** against **74.8%** for Opus 4.5 alone, a **12.2 point** gap as they state it, and Opus 4.5 with Opus 4.5 subagents at **92.3%**, with **3 to 8** samples per problem ([Claude Opus 4.5 system card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)). CORE-Bench went from **42%** to **95%** for Opus 4.5 after rigid grading, ambiguous specs, and stochastic tasks were fixed and a less constrained scaffold was used, so that jump mixes the grader and the harness ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). Harness² reports one optimization step, weights fixed, improving GLM-5 and Gemini 3.5 Flash by up to **11.5 points** on WorkBuddy-Bench, **4.5 points** on JobBench, and **11.8 points** on LAB’s partial pass rate ([Harness²](https://github.com/google-research/harness2)). AutoHarness trains a code verifier until legal-action rate hits **1.0**. On held-out rollouts it reports **100%** legal actions across **145** games. With the prompt held constant, Flash plus that verifier won **64.8%** of two-player matches against vanilla Flash and won **12 of 16** games. The paper attributes **78%** of Gemini 2.5 Flash’s losses in a Kaggle chess competition to illegal moves, a figure from the competition rather than from the paper’s own match tables ([AutoHarness](https://arxiv.org/html/2603.03329)). Harness-Bench freezes the task, the sandbox, and an artifact oracle, lets each native harness keep its own loop, and scores once per task-model-harness cell. A safety or risk-gate failure zeros the task. GPT Sol’s full-credit rate varies by **9.12 points** across seven harnesses even though the standard deviation of its mean scores is **1.93**. GLM variants show full-credit gaps of **13.50 points** ([Harness-Bench](https://arxiv.org/html/2605.27922v2)).

The long-running coding harnesses are reported as design episodes, with cost and duration, and without a frozen pass rate. Anthropic’s November 2025 harness uses the Claude Agent SDK. An initializer and a coding agent share the system prompt, the tools, and the harness, and differ in the initial user prompt. The coding agent is told to verify in the browser, because without that prompt it would unit-test or curl and miss an end-to-end failure. The feature list is JSON on the claim that the model is less likely to overwrite it, and the agent is permitted to change only a `passes` field ([Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)). The March 2026 successor adds a planner, a generator, and an evaluator that fails a sprint when any criterion is under a hard threshold. Early evaluator runs found real bugs and then approved the work anyway. The author retuned the prompt until the logs matched their judgment. One comparison, on a single app prompt, is **20 minutes and $9** for a solo agent against **6 hours and $200** for the full harness. The stated design rule is that every harness component encodes an assumption about what the model cannot do, and that those assumptions go stale as the model improves. Opus 4.6 was the reason they dropped the sprint construct ([Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps)).

Release tables continue to report the joint score, with trial counts that differ by suite. Opus 4.5 averages five trials on the capability table: SWE-bench Verified **80.90%** with thinking off, OSWorld **66.26%** at 1080p and 100 steps, WebArena pass@1 **65.3%** rising to pass@4 **72.4%** on the official grader. Opus 4.6 averages five trials in general, **25** trials for SWE-bench, and prints **80.84%** on Verified. A prompt that pushed tool use, tests first, and root-cause search is associated with **81.4%**, and the card does not state whether that figure is also a 25-trial average. OSWorld-Verified is **72.7%** over five runs ([Claude Opus 4.5 system card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf), [Claude Opus 4.6 system card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)). OpenAI’s November 2025 Codex-Max post, written before the Verified retirement, prints SWE-bench Verified at **77.9%** for GPT-5.1-Codex-Max at extra-high effort on all **500** tasks, and Terminal-Bench 2.0 at **58.1%** in the Harbor harness with compaction on ([GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/)). The deep-research card’s SWE-bench pass@1 uses five patch attempts under Agentless and four under the internal scaffold, on a fixed subset of **477** tasks, with bootstrap intervals that resample attempts and treat the dataset as fixed ([Deep research system card](https://cdn.openai.com/deep-research-system-card.pdf)). Google’s public agent headlines are the same shape. Project Mariner is reported at **83.5%** on WebVoyager as a single agent, without a grader spec on that announcement page. The MKA launch freezes Stirrup and grades deliverables: **200** private tasks, **10** public, roughly **70** yes-or-no checks weighted **75%** factual accuracy and **25%** visual design, an autorater on a non-Google model that agreed with domain experts **96%** of the time on the outputs those experts graded, and models using **30 to 130** turns. Gemini 4 Carbon is described as second in quality and **6×** cheaper than the leader ([Gemini 2.0 announcement](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/google-gemini-ai-update-december-2024/), [MKA benchmark](https://blog.google/innovation-and-ai/models-and-research/gemini-models/multimodal-knowledge-agent-benchmark/)).

## Launch sweeps are the record, and CI gates are the advice

What the labs tell a builder to automate is a regression on every change. What they document about their own frontier agents is a sweep during training or before launch, plus production monitoring. Anthropic writes that automated evals are useful in CI/CD “on each agent change and model upgrade,” and that the useful maintenance split was a dedicated evals team owning infrastructure while product teams write tasks and run the evals. The Claude Code paragraph in the same essay says evals for concision, file edits, and over-engineering were added after employee and user dogfooding, and that they sit alongside production monitoring, A/B tests, and user research. That paragraph does not say the suite is a merge gate, and it publishes no item count or threshold ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). OpenAI’s deep-research card says evaluations ran throughout training, including a final sweep before launch, and that production numbers can move with the system prompt and other parameters ([Deep research system card](https://cdn.openai.com/deep-research-system-card.pdf)). The February 2026 harness-engineering post, about an internal product built with Codex, reports linters and documentation CI, “minimal blocking merge gates,” and flakes handled with follow-up runs. Humans write acceptance criteria and check outcomes. The post publishes no agent-trajectory pass rate ([Harness engineering](https://openai.com/index/harness-engineering/)). Google’s ADK and agents-cli docs tell the reader to fail CI on a missed threshold. The September 2026 post about Google’s own coding-agent work says the opposite of a hard single-run gate: batch the evals, track the aggregate, and keep a single noisy run from blocking a pull request. Behavioral checks in that post are described as local tests that finish in under five seconds. The post publishes no suite size and no pass rate ([Anatomy of harness engineering](https://developers.googleblog.com/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/)).

Judges decide some published scores, and the labs also publish evidence that the judge prompt moves the number. BrowseComp-Plus in the Opus 4.5 card uses Claude Sonnet 4.5 with a three-way match, no-match, or uncertain label. Regrading the authors’ GPT-5 transcripts with Anthropic’s prompt moved GPT-5 from **70.12%** to **72.89%** on the same transcripts. WebArena’s official functional grader had its fuzzy-match subgrader switched from GPT-4 to Sonnet 4.5 with a rewritten prompt. The τ2-bench Airline score for Opus 4.5 moved from **70.1%** to **87.8%** after task-setup and grading fixes, including policy loopholes, with Opus 4.1 simulating the user. The Opus 4.6 card omits Airline because those fixes were not upstream, and it reports Telecom at **99.25%** and Retail at **91.89%** over five trials ([Claude Opus 4.5 system card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf), [Claude Opus 4.6 system card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)). OpenAI’s January 2025 computer-use eval uses gpt-4o as the WebVoyager automatic judge and prints no human-agreement rate on the extra-information note. Operator’s safety numbers grade the deployed agent: confirmation recall **92%** on **607** tasks across **20** risky-action categories, prompt-injection susceptibility **23%** after mitigations against **62%** with none and **47%** with prompting only, across **31** checkable scenarios, and a separate monitor at **99%** recall and **90%** precision on **77** red-team attempts. A manual review of failures left one truly concerning case ([Operator system card](https://openai.com/index/operator-system-card/), [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)). Inspect, the AISI eval framework, freezes the grade token (`GRADE: C` or `GRADE: I`) and binds extraction to the last grade so a token planted in the model’s text does not win. An unparsable verdict is unscored, with no retry. The grader often runs at a nonzero temperature, and the docs say temperature 0 reduces run-to-run disagreement and does not remove it ([Inspect model grading](https://inspect.aisi.org.uk/model-graded.html)).

The consistency metrics they recommend are mostly absent from the tables they print. Anthropic defines pass@k as the chance of at least one success in k trials, and pass^k as the chance that all k succeed. The essay says coding products usually care about pass@1, and products that must behave every time care about pass^k. At k of 10, in their illustration, pass@k approaches **100%** while pass^k falls toward **0** ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). The WebArena series they publish is the rising pass@k curve, **65.3%** to **72.4%** from one to four trials. The opened cards do not print pass^k for a Claude product. OpenAI’s deep-research launch is an exception on the research side: GAIA is reported as pass@1 and as cons@64, a consistency figure, alongside Humanity’s Last Exam at **26.6%** with browsing and a Python tool ([Introducing deep research](https://openai.com/index/introducing-deep-research/)). METR’s March 2024 protocol, written as a capability-elicitation method, says task success varies widely across repeats even at temperature 0, and that a safety case whose 95% interval still contains the threshold should add runs or treat the model as above the threshold. On the GPT-4o application of that method, each agent-task pair ran **10** times, infrastructure errors under **3%** were dropped, and a review of **152** failed runs classed **78 (51%)** as spurious failures fixable with task-agnostic elicitation. Patching one of those patterns succeeded in **4 of 10** previously failed runs ([METR protocol](https://metr.org/blog/2024-03-15-example-autonomy-evaluation-protocol/), [METR GPT-4o report](https://metr.org/evaluations/gpt-4o-report/)).

Injected tool failures, memory stores, and approval gates are specified as builder tests more often than they appear in a launch eval. Anthropic’s opened pages describe natural tool errors returned to the model, a unique string-replace match that otherwise fails and lets the same trial retry, and held-out Slack and Asana tool sets whose chart values are not printed in the article text. They do not describe an eval that injects a scripted fault rate and scores recovery. OpenAI’s realtime guide does: mock the tool, inject one error, and promote a discovered failure into a scripted episode. That pattern is absent from the Codex, Operator, and deep-research launch pages that were opened ([Realtime eval guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)). Conductor’s guide tells a builder to script the model with `mock_run`, replay a known-good trace, and, for every write tool, assert approval-before-write, a rejected approval that blocks the write, a retry of only the failed task, and cancellation with no new write ([Conductor agent evals](https://conductor-oss.github.io/conductor/devguide/ai/agent-evals.html)). Kohl and coauthors, writing from BMW Group and AWS, report the closest production version of that idea: mock the model, assert OpenTelemetry spans for expected tool names and inputs, and stop the pipeline on a failed assertion. They say they run that pyramid for each agent release triggered by a prompt, model, or data change, and they do not print pass rates for the case studies ([Kohl et al.](https://arxiv.org/html/2601.18827)). Memory, as its own score, shows up in the BrowseComp-Plus ablation above and in a Microsoft example that splits a log just before a `retrieve_memory` call. Project Astra’s “up to 10 minutes of in-session memory” is described without a separate memory eval ([Gemini 2.0 announcement](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/google-gemini-ai-update-december-2024/)). Computer Use describes an out-of-model safety check before each action and does not publish a pass rate for that gate ([Gemini 2.5 Computer Use](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-computer-use-model/)). A 2026 engineering post sets a numeric bar for letting a judge block a merge, agreement with humans in the **0.41 to 0.60** band, and the opened text does not cite a calibration study for that band ([The Agentic Harness](https://theagenticharness.co/posts/building-an-llm-eval-pipeline-in-ci-cd-for-agent-changes)). The bar with a published human comparison remains Meta’s verifier study and MKA’s **96%** autorater agreement.

## Conclusion

The eval that the ablations support is a deletion test. Freeze the weights, remove or swap one harness piece, and ask whether an environment score moves by more than the noise floor the same lab already quantified, about **3 points** once machine limits and sampling error are admitted, and closer to **6 to 13 points** when the piece is the scaffold, the memory tool, the subagent split, or a legality gate. Anthropic’s March 2026 design rule, that a harness component is an assumption about a model weakness and should be stress-tested because it goes stale, is that deletion test stated as engineering. The release cards institutionalize the complementary measurement, a pinned pair at launch, which is the right instrument for “how good is this agent” and the wrong instrument for “did this prompt, tool, gate, or memory change earn its keep.”

A team that installs both published lessons ends up with a short stack nobody’s launch card claims as a single system. Hidden tests or a side-effect oracle decide correctness, the way SWE-bench, Meta’s write graph, and AutoHarness’s legality check already do. The trace asserts only the invariants that must not vary: an approval before a write, a tool that must not run, a budget, a secret that must not appear. A judge is a second instrument with a published human-agreement number, sampled, and kept off the seat of the model under test. Trials are numerous enough that a **3 point** harness effect is visible, and a case that passes only because it was rerun stays a fail. Exact trajectory match remains available for a one-step tool whose correct call is unique, which is the case Google’s coding-agent post still allows, and it is a poor default for a multi-step coding agent, which is the brittleness Anthropic documents and ADK’s 1.0 default would encode. The opened record shows each piece in use somewhere. It shows the joint launch score everywhere. It does not show a lab refusing a harness change because that stack failed.
