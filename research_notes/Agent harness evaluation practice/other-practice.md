## What definition of harness or scaffold do these sources use?

### Takeaway
Current Microsoft, Arize, and 2026 papers define a harness as the runtime around the model: loop, tools, context, memory, approvals, and stopping. AISI and METR use "scaffold" for the same elicitation wrapper, and AISI's 2026 playbook equates solver, scaffold, and harness. Meta's 2025 paper mostly holds one ReAct orchestration fixed and evaluates write actions inside an environment, rather than defining a product harness.

### Cited Findings
- Reported glossary, AISI playbook, page opened, no displayed revision date: "Solver" is "Also known as" "scaffold, harness", and is "The structure put in place to let the model attempt the task, from simple prompting through chain-of-thought to a full agent loop." A "Run" is "Also known as" "trajectory", "The log (or transcript) capturing every message, tool call, and result." A "Scorer" is "Also known as" "grader, judge". — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)
- Reported framework split, same page: samples are "what" is asked; solvers are "how" behaviour is elicited; "The same samples can be evaluated with different solver strategies (direct prompting, few-shot, chain-of-thought, or a full agent scaffold) and the results compared." Agents "compose solvers, tools, and planning". Inspect "provides a built-in ReAct agent, multi-agent handoffs, and an Agent Bridge for running external agents" inside evaluations. Approvers are "policies for approving, modifying, or rejecting tool calls before execution." — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)
- Reported product definition, Microsoft Learn, page opened, no displayed revision date: "An agent harness, sometimes called an AI harness, is the runtime scaffolding that turns a language model into an agent that can perform work. It drives model and tool calls, manages conversation state and context, applies approval policies, and can keep the agent progressing through a multistep task." The listed composition is chat client, chat pipeline (function invocation, message injection, per-service-call history, optional compaction), context providers (instructions, tools, memory, todo state, modes), and middleware (approval, observability, optional bounded looping). The capability matrix includes function invocation with a per-request iteration limit, compaction, todo tracking, plan/execute modes, file memory, tool approval, OpenTelemetry, skills, background agents, shell, and "Looping: Optional bounded re-invocation driven by evaluators or predicates." — [Microsoft Agent Harness](https://learn.microsoft.com/en-us/agent-framework/concepts/harness)
- Reported vendor definition, Arize, page opened, no displayed date: "An agent harness is the runtime wrapped around a language model that enables it to perform multi-step work. It manages the model-tool loop, context, tools, state, permissions, persistence, retries, delegation, and stopping behavior." Arize separates language model, agent framework or SDK, agent harness, tracing, and "Evaluation harness", and says an evaluation harness "Selects behavior to evaluate, runs scoring, and routes results." Arize says Microsoft's documentation uses a similar runtime definition. — [Arize](https://arize.com/resources/agent-harness-evaluation-tracing/)
- Reported lab definition, METR GPT-4o report, 7 August 2024, older: "our methodology involves using scaffolding programs to make agents out of language models." "All the agents used in this report are derived from essentially the same scaffolding program with only minor modifications. This scaffolding is relatively simple, providing the agent with only bash, python, and answer-submission tools." The loop is "prompting the underlying language model with a transcript of actions and observations so far ... parsing out the next action ... executing it, adding the action and the resulting observation to the transcript, and re-prompting." Context handling inside that scaffold truncates long tool outputs and "the middle of the transcript", always preserving "the task instructions, the first few actions, and the most recent few actions." "Elicitation" is "iteratively modifying an agent in an attempt to improve its performance." — [METR GPT-4o report](https://metr.org/evaluations/gpt-4o-report/)
- Reported minimum scaffold, METR elicitation guidelines, 15 March 2024, older: "The model should be provided with the best available scaffolding + tooling, including at a minimum the ability to do chain-of-thought reasoning, use the command line and see the resulting output, and a way to manage long tasks given context-length limits." If several scaffold versions exist, "you should use the highest-performing version." The authors say the guidelines "should be considered as somewhat informed and reasoned guesses only" and that they "have not yet conducted a full evaluation according to this methodology." — [METR elicitation guidelines](https://metr.org/blog/2024-03-15-guidelines-for-capability-elicitation/)
- Reported environment-and-orchestration split, Meta ARE paper, arXiv:2509.17158, opened; figure caption dates pricing access 10 September 2025: ARE is "a research platform for scalable creation of environments ... each with their own rules, tools, content, and verifiers." "ARE provides a default agent orchestration" that "is a ReAct loop ... with some additions," one tool call per step, "formatted as a JSON," plus pre-step and post-step operations. "any orchestration is compatible with ARE as long as it supports its two core interfaces: tools and notifications." "JSON tool calling remains the standard evaluation method." The paper does not use "harness" for that loop in the sections read. — [ARE paper](https://arxiv.org/html/2509.17158)
- Reported paper definition, Harness-Bench, arXiv:2605.27922, opened; the HTML header does not show a calendar date: "Agent harnesses shape how language models turn instructions into completed work by governing tool use, context management, and execution." They "organize prompts and context, expose tools, manage execution state, and handle errors." Each configuration "retaining its own prompting, tools, context management, and recovery behavior." — [Harness-Bench](https://arxiv.org/html/2605.27922v2)
- Reported paper definition, Zhong and Zhu, arXiv:2605.13357v1, 13 May 2026: a harness is "a runtime substrate" in a "model–harness–environment system" that "mediates how a foundation-model agent observes a project, acts on it, receives feedback, and establishes that a change is complete." They list eleven responsibilities: "task specification, context selection, tool access, project memory, task state, observability, failure attribution, verification, permissions, entropy auditing, and intervention recording." They explicitly say a harness "is not an agent framework" and "is not an evaluation harness: an evaluation harness measures behavior, while a development harness shapes behavior." — [Zhong and Zhu](https://arxiv.org/html/2605.13357)
- Reported engineering usage, The Agentic Harness, Dmitri Okonkwo, 24 September 2026, updated 5 November 2026: the post treats "a harness layer" as "prompt, tool schema, workflow, memory, or skill." — [The Agentic Harness](https://theagenticharness.co/posts/building-an-llm-eval-pipeline-in-ci-cd-for-agent-changes)
- AISI bounty definition, search extract only, page not opened. The extract says applications were due in 2024 and stage-two work by 15 March 2025, so this is older: "Agent scaffolding consists of a set of tools, prompting procedures, and error handling to assist the agent in troubleshooting issues that arise from tool-calling." Final submissions "should be in the form of Inspect-solvers." — [AISI bounty post](https://www.aisi.gov.uk/blog/evals-bounty)
- Magentic-One and AutoGenBench, pages not opened. Search extracts describe an Orchestrator with an outer task ledger and an inner progress ledger, and AutoGenBench as a tool "for running agentic benchmarks that allows repetition and isolation, e.g., to control for variance of stochastic LLM calls and side-effects." Those sentences are not quoted here as opened-page text. — [Microsoft Research article, not opened](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)

### Inferences
- By late 2026 the word "harness" in Microsoft, Arize, Harness-Bench, and Zhong and Zhu means the runtime control layer. In 2024 METR, and still in the AISI playbook, "scaffold" means the elicitation program wrapped around a model for a capability eval. The AISI playbook is the source that states the synonymy directly.
- Meta's published method evaluates an agent inside a simulated world with a verifier. The orchestration is described as a default ReAct loop held constant across models, which is a scaffold in the METR sense, not a named harness product.

### Gaps
- Conductor's eval guide, which was opened, does not define "harness" or "scaffold". It defines an eval as a test of an agent.
- No opened page from Microsoft, Meta, AISI, METR, or LangSmith states a formal distinction between "scaffold" and "harness" other than the AISI glossary row and Zhong and Zhu's distinction between a development harness and an evaluation harness.
- The Magentic-One primary article was not opened, so its definition of the multi-agent loop is not recorded as a quotation.

## Which checks are deterministic, and which are judged?

### Takeaway
Deterministic checks in the opened sources are exact or scripted comparisons of tool name, arguments, order or allowed set, guardrail outcome, write-action causality, and final artifact oracles. Judged checks are model graders over open answers, trajectory quality, or soft equivalence of message content. Meta is the source that publishes both in one verifier and then measures that verifier against human labels.

### Cited Findings
- Reported, AISI playbook: "`exact()` matching is fast and deterministic but brittle to valid variations in phrasing. `model_graded_qa()` handles paraphrasing and nuance but is non-deterministic and costs money to run." The tool-using pattern is "scored at checkpoints along the way." inspect_cyber, described on the same page, uses "Ordered checkpoints for partial-credit scoring" and "Solution verification" that validates "an evaluation is correctly configured and solvable before spending on model runs." Inspect Scout scanners include "Command errors: Is the model trying to use tools it doesn't have access to". — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)
- Reported, Inspect model grading, page opened: the default instructions ask for a grade "in the format `GRADE: C` or `GRADE: I`", extracted by `grade_pattern`. "`include_history`" defaults to false, so only the original sample input is presented unless set. A panel uses the `"majority"` reducer: "A grade wins only when more than half of the panel returns it"; an unparsable grade "withholds its vote"; otherwise the sample is unscored. "An unparsable verdict produces `Score.unscored(reason="grader_failed")` without retrying." Metrics on `model_graded_qa` are `accuracy()` and `stderr()`. Grade extraction "binds to the last grade" so an earlier `GRADE: C` in chain-of-thought or injected via the submission does not win. Templates neutralize `[BEGIN DATA]` / `[END DATA]` markers inside model-controlled text. — [Inspect model grading](https://inspect.aisi.org.uk/model-graded.html)
- Reported, Microsoft evaluation page, opened: `LocalEvaluator` "runs checks locally without API calls". Built-in checks: `keyword_check` requires all keywords; `tool_called_check` requires named tools to have been called; `tool_calls_present` requires all `expected_tool_calls` names, "unordered, extras OK"; `tool_call_args_match` requires name and arguments, "subset match on args". A custom check may return `bool`, `float` with "≥ 0.5 = pass", or a dict with `score` or `passed`. `FoundryEvals` is "cloud-based LLM-as-judge evaluation." Default Foundry evaluators are relevance, coherence, and task adherence, and "When items contain tool definitions, it automatically adds tool call accuracy." Named tool-usage judges: `tool_call_accuracy`, `tool_selection`, `tool_input_accuracy`, `tool_output_utilization`, `tool_call_success`. Named agent-behavior judges: `intent_resolution`, `task_adherence`, `task_completion`, `task_navigation_efficiency`. "Python agent responses retain schema-only snapshots of function tools." "Automatic discovery raises `ValueError` if a called tool used different input schemas under the same name." "Tool input schemas must contain JSON-compatible values." The page shows a `split_before_memory` example that splits a conversation "just before a memory-retrieval tool call" named `retrieve_memory`. — [Microsoft agent evaluation](https://learn.microsoft.com/en-us/agent-framework/agents/evaluation)
- Reported, LangSmith trajectory page, opened: trajectory match "is deterministic, fast, and cost-effective since it doesn't require additional LLM calls." Modes: `strict`, "Exact match of messages and tool calls in the same order", with the example "policy lookup before authorization"; `unordered`, "Same tool calls allowed in any order"; `subset`, "Agent calls only tools from reference (no extras)"; `superset`, "Agent calls at least the reference tools (extras allowed)." "`strict` mode ... allows for differences in message content." Default tool equality is "only tool calls with the same arguments to the same tool", overridable with `tool_args_match_mode`. The LLM-as-judge alternative "is less deterministic" and is for "efficiency and appropriateness" "without strict tool call or ordering requirements." The documented judge is `create_trajectory_llm_as_judge` with `prompt=TRAJECTORY_ACCURACY_PROMPT`. The judge "doesn't require a reference trajectory, but one can be provided." — [LangSmith trajectory evals](https://docs.langchain.com/langsmith/trajectory-evals)
- Reported, Meta ARE paper: verification compares "agent write actions only to annotated oracle write actions." Read actions are excluded "since multiple reading strategies can lead to the correct set of write actions." A preliminary check requires "used tool names counters" to be identical. Then, in topological order: a hard check "for parameters that require exact matching" and a soft check where "an LLM judge is prompted with the user task" and "determines if the actions are equivalent according to tool-specific guidelines." After RL "hacking of the verifier", they "add a soft check for global sanity of the agent's messages." Causality: parents in the oracle graph must already be matched; independent siblings may occur in either order. Timing must fall "within a specified tolerance window." Success requires every oracle action to match. "the verifier implicitly assumes there are no equivalent write actions"; using a different app than the oracle "will trigger a failure." They prefer write-action sequences over final state because the sequence can "distinguish ... a Mobile trajectory where the agent adds an event at the wrong place and correct itself from a trajectory where the agent is correct at first try." — [ARE paper](https://arxiv.org/html/2509.17158)
- Reported, ARE judge reference, opened via fetched page text: `ScriptedGraphPerEventJudge` "uses purely deterministic, scripted validation without LLM-based soft validation" and "Completely deactivates soft judges." Checker types named: `eq_checker`, `contain_any_checker`, `contain_all_checker`, `unordered_list_checker`, `path_checker`, `phone_number_checker`, `datetime_checker`. Time tolerances in the example are `pre_event_tolerance_seconds=5.0` and `post_event_tolerance_seconds=20.0`. `HardToolJudge` is "scripted, deterministic checks on tool arguments." `SoftToolJudge` does an "Equality Pre-check" to skip an LLM call when arguments are identical, then soft checkers including `content_checker`, `signature_checker`, `sanity_checker`, `placeholder_checker` (rejects text such as "[User's Name]"), `email_checker`, `message_checker`, `tone_checker`. "Returns success only if all checkers pass." `InContextJudge` is "A baseline judge that uses LLM-based evaluation by providing all agent and oracle events in context." — [ARE judge system](https://facebookresearch.github.io/meta-agents-research-environments/api_reference/validation.html)
- Reported verifier measurement, ARE paper Table 1, 450 human-labeled trajectories, same judge model Llama 3.3 70B Instruct: In-context verifier (LLM judge only) agreement 0.72, precision 0.53, recall 0.83. ARE verifier agreement 0.98, precision 0.99, recall 0.95. The in-context judge "tends to accept agent trajectories too readily." Prompts "were tuned for Llama 3.3 70B Instruct" and then reused for Gemini 2.5 Pro and Claude Sonnet 3.7; the paper says those three "have satisfactory precision scores" and points to Table 5, which was not copied here. — [ARE paper](https://arxiv.org/html/2509.17158)
- Reported, METR GPT-4o report, older: tasks "receive a score between 0 and 1." Aggregation ran each agent-task pair "10 times", "Filtered out runs which errored out for non-agent reasons (<3%)", then averaged within task and across tasks with family and difficulty weights. Of 152 reviewed failed runs, 68 (45%) were classed "real" capability limits, 78 (51%) "spurious" and "easily fixed with task-agnostic elicitation", 6 (5%) "tradeoffs" fixable with "task-specific scaffolding changes." A manual patch of one spurious pattern, resampling unsupported conclusions, "succeeded in 4 out of 10 previously failed runs." The protocol page says scoring follows "the scoring guidelines for each task (if not automatically scored)." — [METR GPT-4o report](https://metr.org/evaluations/gpt-4o-report/); [METR protocol](https://metr.org/blog/2024-03-15-example-autonomy-evaluation-protocol/)
- Reported, Harness-Bench: "Task-specific oracles score final artifacts, awarding partial credit for completed modules under safety and risk gates." Score \(Q_i = g_i \sum_j w_{ij} x_{ij}\), with \(g_i = 0\) when any safety or risk gate fails, "for protected-resource tampering, sensitive-data disclosure, or prohibited actions." "Ordinary errors lose only the affected modules' credit." The related-work section says the study asks "how specific workflow requirements, verified without a model judge, change harness preferences." "Reference solutions are executed and receive full credit on every task." "Each task–model–harness combination is evaluated once." — [Harness-Bench](https://arxiv.org/html/2605.27922v2)
- Recommendation, Conductor, page opened, no date: "Make routing and side-effect policy deterministic before judging prose quality." Deterministic assertions named: `assert_tool_used`, `assert_tool_not_used`, `assert_tool_called_with`, `assert_tool_call_order`, `assert_tools_used_exactly`, output contains or regex, status, max turns, event sequence, handoff, `assert_guardrail_passed`, `assert_guardrail_failed`. Quality is "An optional LLM judge scoring groundedness or usefulness" via `assert_output_satisfies` with an explicit `model` and `threshold`. The example threshold is `0.8` and the example criterion string is "The answer cites only supplied evidence and clearly states uncertainty." — [Conductor agent evals](https://conductor-oss.github.io/conductor/devguide/ai/agent-evals.html)
- Recommendation, Arize: "Use code when the requirement can be stated unambiguously." Examples: "A tool argument must conform to a JSON schema." "A refund cannot occur before authentication." "A file-writing operation requires an approval event." "A completed transaction must return a transaction ID." "An agent may not exceed a defined number of tool calls." Use a model judge for groundedness, rubric following, handoff completeness, and whether an answer is "relevant, clear, and actionable." "Sensitive actions should be enforced through deterministic permissions, hooks, and approval mechanisms that do not depend on the model voluntarily following an instruction." — [Arize](https://arize.com/resources/agent-harness-evaluation-tracing/)
- Reported method plus case studies, Kohl et al., BMW Group and AWS, arXiv:2601.18827, opened; calendar date not in the HTML header: structural tests compare "expected behavior ... with the real behavior as captured by traces" using OpenTelemetry spans. "For agent components with deterministic behavior, defining and checking structural tests works the same as in software engineering." The LLM is the non-deterministic part, so they mock it. Listing 1 asserts tool invocations `get_customer_information` and `update_customer_information` and an input object containing `ucid` and `phoneNr`. — [Kohl et al.](https://arxiv.org/html/2601.18827)
- Proposal, Zhong and Zhu: principle P3 says "Task completion is bound to evidence—deterministic checks, targeted tests, regression attempts, lint, patch review—rather than to a natural-language assertion." Their validation task "yields episode packages whose evidence structure varies systematically with harness level: lower levels produce only a final patch, higher levels produce reproduction logs, failure attributions, deterministic requirement checks, and structured verification reports." That is one controlled task, described as a research program, not a multi-benchmark result. — [Zhong and Zhu](https://arxiv.org/html/2605.13357)

### Inferences
- "Tool schema" appears as a deterministic object in Microsoft (schema snapshots and a collision error), LangSmith (argument equality), Arize (JSON schema), and Kohl et al. (asserted tool input). None of the opened lab protocols say they unit-test JSON Schema validation as a separate harness gate. They test whether the observed call matches an expected call.
- Authorization is a runtime mechanism in AISI approvers and Microsoft tool approval. It becomes a test assertion in Conductor (guardrail failed, write only after approval) and in Arize's recommended checks (refund before authentication, approval event before file write). Meta and METR do not describe an authorization assertion.
- Idempotency is named only by Conductor, as a cancellation case: "reconcile ambiguous in-flight writes by idempotency key or marker." Meta's write-sequence verifier catches a wrong write that was later undone, which is a side-effect check, and the paper does not call it idempotency.
- Memory is a harness feature in Microsoft and a span type in Kohl et al. ("accessing memory"). The opened eval docs do not score memory quality except by splitting the conversation at a retrieval call or by listing memory as something a trace should contain.

### Gaps
- No opened source states a deterministic check whose subject is "the gate passed" as a boolean computed by the harness and then re-checked by a second gate. Conductor and Arize tell the builder to assert that a guardrail fired. AISI and Microsoft document the approval mechanism, not a test that the approval mechanism cannot be bypassed.
- METR's 0–1 task scores are described as task scoring guidelines, often automatic. The opened pages do not publish the per-task scoring code or say whether any score is a model judge.
- LangSmith's CI page says offline evals have "Assertions: Hard and Soft" in a diagram and does not define those words on that page. The trajectory page is the source for the deterministic-versus-judge split.

## Do they put any of this in CI? What do they say about a model judge as a merge gate, variance, and frozen wording?

### Takeaway
Microsoft, LangSmith, Conductor, Kohl et al., and the 2026 engineering posts tell builders to run deterministic trace checks in CI. The sources that discuss a model judge as a blocking gate say to pin the judge and rubric, expect variance, and not treat an uncalibrated judge as the only merge gate. AISI freezes the grade token and extraction regex. Meta freezes prompts across judge models and reports agreement, and does not describe CI. METR, in 2024, requires repeated runs and confidence intervals because success varies even at temperature 0, and does not describe a merge gate.

### Cited Findings
- Reported product guidance, Microsoft Foundry evaluation, opened: "Pin datasets, model deployments, evaluator versions, and rubric versions when results must be comparable across runs. Use result assertion helpers to fail CI when required metrics regress." The same page says ".NET samples also demonstrate Foundry rubric evaluators and per-dimension quality gates." It does not say an LLM judge is forbidden as a merge gate, and it does not discuss frozen judge wording beyond pinning "rubric versions". — [Microsoft Foundry evaluation](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/evaluation/microsoft-foundry)
- Reported, Microsoft evaluation page: `LocalEvaluator` is "ideal for inner-loop development, CI smoke tests, and fast iteration." `evaluate_agent` "runs the agent once per query" unless `num_repetitions` is set. The repetitions section is titled "Measure consistency with repetitions" and says "Run each query multiple times to detect non-deterministic behavior." The example uses `num_repetitions=3`. `r.raise_for_status()` "Raises EvalNotPassedError if any item failed." — [Microsoft agent evaluation](https://learn.microsoft.com/en-us/agent-framework/agents/evaluation)
- Reported, LangSmith CI page, opened, no date: the example pipeline's testing block includes unit, integration, end-to-end, and "Offline evaluations" using "AgentEvals, OpenEvals and LangSmith", with a node "Assertions: Hard and Soft", then "Promote to Production if All Pass". Triggers include "Code or Graph Change", "Prompt Commit in PromptHub", and "PR Opened". Trajectory evaluation in that pipeline "evaluates whether your agent invoked the right tools in the right order or at the right time." The page does not mention judge variance, a frozen judge prompt, or a rule that a model judge must not block a merge. — [LangSmith CI/CD example](https://docs.langchain.com/langsmith/cicd-pipeline-example)
- Reported, LangSmith trajectory page: the pytest-style examples `assert evaluation["score"] is True` for both `strict` match and the LLM judge (`test_trajectory_quality`). That is a boolean gate around the judge score in the documented test, not a discussion of variance. The judge prompt used in the sample is the constant `TRAJECTORY_ACCURACY_PROMPT`. The page does not say to freeze that string or to measure judge agreement. — [LangSmith trajectory evals](https://docs.langchain.com/langsmith/trajectory-evals)
- Recommendation, Conductor: "Run a small deterministic suite on every change." "An LLM judge is probabilistic and has cost. Pin the judge model and threshold, run it separately from fast CI when appropriate, and include deterministic checks that prevent unsafe paths even if the judge is unavailable." Release ladder: unit tests; "Trace assertions: mocked or replayed agent results"; "Live correctness evals"; "Semantic evals"; production monitoring. "Use a failure in layers 1–3 as a release blocker for a safety or routing invariant. Treat semantic scores as a quality signal with a documented threshold and human review for boundary cases." The page does not report a measured agreement statistic. — [Conductor agent evals](https://conductor-oss.github.io/conductor/devguide/ai/agent-evals.html)
- Recommendation, Arize: "LLM judges should be evaluated too. Their prompts, labels, and rubrics should be calibrated against human-reviewed examples, particularly when their scores control alerts or deployment gates." A listed destination for an evaluation score is "A CI/CD gate." The FAQ answer is "Should every agent evaluation use an LLM-as-a-judge? No. Use deterministic code for requirements that can be tested directly, such as schemas, permissions, required tool calls, thresholds, and transaction status. Use model-based judges for semantic or open-ended qualities, and calibrate them against human labels." No agreement coefficient is stated on the opened page. — [Arize](https://arize.com/resources/agent-harness-evaluation-tracing/)
- Recommendation, The Agentic Harness, 24 September 2026, updated 5 November 2026: "Deterministic metrics (exact match, tool call correctness, schema conformance) run on every pull request and block merges automatically." A judge "block[s] a merge only when the judge has cleared the 0.41 to 0.60 moderate-agreement threshold with human reviewers." Later: "a judge needs to reach at least the 0.41 to 0.60 range of what's typically called 'moderate' agreement with human reviewers before its verdict should ever block a pull request. Below that threshold, the metric still has value as something to track ... but it lacks the authority to stop a merge." "What actually blocks a merge should be narrow and specific: deterministic metric failures, and calibrated-judge scores that fall below an agreed threshold ... tied specifically to production trace replays where the previous version is known to have passed." Gray zone, "any metric the judge is tracking but hasn't yet cleared the 0.41 to 0.60 agreement floor", and thin samples "flag for human review instead of blocking." The post says these "do not belong in this stack as a CI gate: token usage, latency by itself, and single-run pass/fail without pass@k." The opened text does not cite a study for the 0.41–0.60 band and does not discuss freezing judge wording. A duplicated paragraph and an unsourced "14%" opening scene are in the page; those are not recorded here as measurements. — [The Agentic Harness](https://theagenticharness.co/posts/building-an-llm-eval-pipeline-in-ci-cd-for-agent-changes)
- Reported grading controls, Inspect, not described as CI: "By default the grader model runs with the provider's default generation settings. In practice this often means a non-zero temperature (e.g. 1.0) and no fixed seed, so grades for borderline answers can change from run to run and across epochs." `model_graded_qa()` "do not take a generation `config` argument." The documented way to pin generation is `get_model(..., config=GenerateConfig(reasoning_effort="none", temperature=0))`. "The OpenAI Responses API, which Inspect uses by default for GPT-5 and later, does not accept `seed`." Reproducible-grading list: temperature 0 where accepted; a seed where supported; "Run multiple `epochs` and inspect grade variance — setting `temperature=0` reduces, but does not always eliminate, run-to-run disagreement." The grade wording that is frozen by code is the `GRADE: C` / `GRADE: I` token and the default regex, not a prose rubric hash. Custom instructions require a matching `grade_pattern`. — [Inspect model grading](https://inspect.aisi.org.uk/model-graded.html)
- Reported variance guidance, AISI playbook, not described as a product merge gate: "Run the same evaluation twice and you may get different results." Reliability "only emerges across many runs." The page names "pass@k (probability of at least one success across k trials), and confidence intervals that account for variance." "A result is only interpretable next to the limits that produced it." Eval sets do "automatic retry with exponential backoff" and "sample preservation across failures." — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)
- Reported variance, METR protocol, 15 March 2024, older: "In our experience, the variance in task success can be large across repeated runs, even with identical agents and task prompts, and even when using T=0 for generation." If a safety case needs 95% confidence that performance is below a threshold, and the 95% interval still includes the threshold, "you should either run all tasks again, and repeat until your 95% CI is below the threshold (including a correction for early stopping), or decide to treat the model as above the threshold." "A threshold that is based on 'does the model do this at least once' is suboptimal because it is very high variance." Transcript check: for non-max scores, "have someone read over the run transcripts" and "Make sure that this is not to do with problems with the task, scoring, infrastructure, or scaffolding." The page does not mention CI or a model judge as a gate. — [METR protocol](https://metr.org/blog/2024-03-15-example-autonomy-evaluation-protocol/)
- Reported, Meta: the verifier is evaluated with perturbation "unit" tests and with the 450-trajectory human comparison in Table 1. "same prompts were used for all models." The paper records verifier hacking during RL as a reason for an extra sanity check. No CI or merge-gate language appears in the verification sections read. — [ARE paper](https://arxiv.org/html/2509.17158)
- Reported practice in the paper's case studies, Kohl et al.: "these tests can be integrated into a CI/CD pipeline, enabling automated test runs for each change. This also prevents deploying faulty agents, as the pipeline stops in case of a failed assertion." "We run the pyramid for each new agent release, which is triggered by changes such as updated prompts, models, or data." They say a mocked-LLM test "can be run and evaluated automatically in a CI/CD pipeline" when the pass/fail is checkable from traces. They point to a travel-agent example "detailing methods, framework, and CI/CD pipeline" on GitHub; that repository was not opened. — [Kohl et al.](https://arxiv.org/html/2601.18827)
- Reported, Harness-Bench: one run per task-model-harness pair. The paper does not describe CI. It does report harness sensitivity: "We measure each model's sensitivity as the SD of its seven harness-specific mean scores." For GPT Sol, "its full-credit rate varies by 9.12 percentage points" across harnesses despite an SD of mean score of 1.93. GLM variants have "full-credit gaps of 13.50 points." Those figures are cross-harness spread, not repeated-run variance of one harness. — [Harness-Bench](https://arxiv.org/html/2605.27922v2)

### Inferences
- The builder-facing docs that were opened (Microsoft, LangSmith, Conductor) put a failing deterministic assertion in the automated path. They differ on the judge: Microsoft tells you to pin versions and fail CI on regressed metrics, which can include Foundry judge metrics; Conductor says to keep the judge off the fast blocking path; LangSmith's sample test asserts the judge's boolean score directly.
- Frozen wording, where it exists, is about the grader's output contract (Inspect's `GRADE:` token) or about pinning a rubric version (Microsoft) or reusing the same prompts across judge models (Meta). No opened source says to hash a judge prompt and reject a merge when the hash changes.
- METR's variance warning is about the agent under test, including at temperature 0, and the remedy they publish is more runs and confidence intervals, plus a human read of transcripts for scaffold bugs. That is lab protocol from 2024, not a CI system.

### Gaps
- No opened page states a numerical variance budget, such as a maximum standard error, for a model judge used as a merge gate.
- Inspect's own repository CI for the Inspect framework was not opened. The playbook describes evaluating models with Inspect, not a pipeline that blocks a product merge on `model_graded_qa`.
- The LangSmith pytest announcement of 22 January 2025 was not opened. The CI claims above come from the current CI guide and the trajectory guide.
- Magentic-One's AutoGenBench repetition and isolation claims were not taken from an opened page.

## What concrete case shape do they recommend: world, scripted model, expected trace, expected side effect?

### Takeaway
Two shapes are published. Lab evaluations use a world plus a live model: AISI sandbox and target, METR virtual environment and 0–1 score, Meta simulated apps and an oracle graph of write actions, Harness-Bench a sandbox and an artifact oracle. Builder tests use an expected trace or a scripted model: LangSmith's reference message list, Conductor's `mock_run` and `replay`, Kohl et al.'s mocked LLM and span assertions, Microsoft's expected tool calls on a live or logged conversation.

### Cited Findings
- Reported, AISI: a task is dataset of samples, solver, and scorer. A sample can carry "metadata, sandbox configuration, and files to inject into execution environments." The homepage CTF example, from the Inspect homepage search extract and consistent with the playbook's agent pattern, uses `solver=react(...)`, `tools=[bash(), todo_write()]`, `attempts=3`, `scorer=includes()`, `sandbox="docker"`. The playbook says the sandbox "holds the environment it is changing". Inference limits recorded with the result are "a token budget, a wall-clock timeout, a maximum number of messages, a finite number of times the agent can submit a solution, or a cap on tool calls." This shape is world plus live model plus target or checkpoint. It is not a scripted model. The Inspect homepage was not fetched as a full page; the playbook was. — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html); [Inspect homepage, search extract](https://inspect.aisi.org.uk/)
- Reported, METR, older: "tasks: specific goals to be carried out in pre-specified virtual environments." "The agent is given a token usage and wall clock time budget, and receives a score between 0 and 1." Humans attempted "the same environments which were presented to the agents." The scaffold is live. The case is a world and an automatic or rubric score, plus a transcript. The opened pages do not specify an expected action trace. Elicitation is done on a dev set; the test set is then run with the chosen scaffold. The protocol says the elicitation team may "make additional tasks" for a train set "in order to improve performance on the dev-set tasks without overfitting." — [METR GPT-4o report](https://metr.org/evaluations/gpt-4o-report/); [METR protocol](https://metr.org/blog/2024-03-15-example-autonomy-evaluation-protocol/)
- Reported, Meta: a scenario has a simulated environment, a task, and "the minimal sequence of write actions needed to solve a task," stored as an oracle graph. Read actions are not gold. The verifier matches write actions on tool, arguments, causality, and timing. `are-benchmark run` executes; `are-benchmark judge` validates offline. The scripted judge maps each oracle event id to checker parameters, which is an expected side effect with per-argument checkers, not a full message trace. They also test the verifier by "perturbations to oracle actions that we know preserve or invalidate the oracle trajectory validity." The paper says those perturbations "do not necessarily reflect real trajectories." — [ARE paper](https://arxiv.org/html/2509.17158); [ARE judge system](https://facebookresearch.github.io/meta-agents-research-environments/api_reference/validation.html)
- Reported, Microsoft evaluation: a case can be a query, an optional `expected_output`, and optional `expected_tool_calls` such as `ExpectedToolCall("get_weather", {"location": "NYC"})`. Alternatively, "evaluate them directly without re-running the agent" from "responses from logs or previous runs", or `evaluate_traces` on response ids. The agent under test is the live harness agent or a captured conversation. The opened pages do not show a scripted stand-in for the model. — [Microsoft agent evaluation](https://learn.microsoft.com/en-us/agent-framework/agents/evaluation); [Microsoft Foundry evaluation](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/evaluation/microsoft-foundry)
- Reported, LangSmith: "Hard-code a reference trajectory for a given input." The reference is a list of messages: human message, assistant message with `tool_calls` (id, name, args), tool message, assistant message. The example input is "What's the weather in Boston?" and the expected call is `get_weather` with `{"city": "Boston"}`. The test invokes a live agent (`create_agent("gpt-6.1-sol", ...)` in the Python sample) and compares `outputs` to `reference_outputs`. That is an expected trace, including expected tool results in the reference, not a separate world state and not a scripted model. — [LangSmith trajectory evals](https://docs.langchain.com/langsmith/trajectory-evals)
- Recommendation, Conductor, with concrete types: an `EvalCase` has `name`, `agent`, `prompt`, and expectations such as `expect_handoff_to`, `expect_tools`, `expect_tools_not_used`, `expect_output_contains`. `mock_run()` "drives an agent through a scripted sequence of events" "with no model call". "Tools still execute by default"; `auto_execute_tools=False` stubs them. `record` / `replay` saves a trace "when the purpose is to preserve a known-good behavior shape, not to retest a live model." Side-effect cases required "For every write-capable tool": safe request with the write "only after approval"; disallowed argument and "the guardrail failure is recorded"; approval rejected and the write task does not run; a retryable failure retries "Only the failed task" while "completed upstream work remains recorded"; cancellation with "No new write" and ambiguous writes reconciled "by idempotency key or marker." "Use a fixture account, sandbox, or fake tool" for email, charges, repository mutation, or commands. — [Conductor agent evals](https://conductor-oss.github.io/conductor/devguide/ai/agent-evals.html)
- Reported method, Kohl et al.: one trace id per user input. Spans include "accessing memory, invoking LLM, or using tools." `mocked_LLM.add_output(...)` scripts the model. Listing 2 "use[s] a mocked LLM for the first part of the conversation" and `add_real_response` switches to a live model "so that we can steer the conversation towards a desired state." Assertions filter traces for expected tool name and input. They describe this as the lower and middle layers of a test pyramid; acceptance tests of the whole system remain the top. — [Kohl et al.](https://arxiv.org/html/2601.18827)
- Reported, Harness-Bench: "300 sandboxed tasks", "input resources, deliverables, and operational constraints." "Each configuration receives identical task inputs and initial environments in an isolated workspace." "Oracles score final artifacts; traces support behavioral and resource analysis." Runs use "a 200K-token input-context threshold, beyond which each harness applies its default context management, and a 150-turn interaction limit." Native harness behavior is preserved. The case is a world plus a live native harness plus an artifact oracle and safety gates. It is not a scripted model or an expected tool trace. — [Harness-Bench](https://arxiv.org/html/2605.27922v2)
- Proposal, Zhong and Zhu: hold "the task, the repository, and the model fixed" and vary harness level H0–H3. H0 is "only the task description and the repository files." The evaluation artifact is an "episode package" with eight evidence classes: "action, tool, context, verification, failure attribution, intervention, entropy, and outcome." Adjudication is "by verification autonomy rather than task success alone." They define M-HIR as missing-harness human interventions divided by total episodes. Applied to "a controlled validation task", not a published suite of cases a builder can import. — [Zhong and Zhu](https://arxiv.org/html/2605.13357)
- Recommendation, The Agentic Harness: "trajectory-level evals built from real production traces" and "Every merged harness change should feed its production traces back into the eval suite." The post argues synthetic happy-path cases miss schema drift, duplicated work, and workflow loops. That is an expected-trace-from-production shape. The post does not specify a scripted model or a world simulator. — [The Agentic Harness](https://theagenticharness.co/posts/building-an-llm-eval-pipeline-in-ci-cd-for-agent-changes)
- Recommendation, Arize: the closed loop is run, capture the trace, evaluate spans, trajectories, outcomes, and sessions, then change "the prompt, context, tool, policy, evaluator, or control loop" and "Run regression tests." A concrete counterexample: a final answer that claims a refund is not enough; the check is "a deterministic evaluation requiring a successful refund span and a valid refund ID." — [Arize](https://arize.com/resources/agent-harness-evaluation-tracing/)

### Inferences
- "World" is the lab shape when the thing being measured can only be seen in the environment: flags, files, write actions, delivered artifacts. "Expected trace" and "scripted model" are the builder shapes when the thing being measured is the loop, routing, or a guardrail, and a live model would make the test flake.
- Microsoft's expected tool call is a thin expected trace on a live or logged run. It does not include the tool's return value. LangSmith's reference trajectory includes tool results and the following assistant message.
- Meta's oracle is deliberately not a full trace. Reads are free. That is the opposite of LangSmith `strict` mode, which matches the message sequence and treats extra tools as failure in `subset` and `strict`.

### Gaps
- No opened source publishes one case file that contains all four of world, scripted model, expected trace, and expected side effect.
- METR does not say whether task scoring inspects the filesystem, a submitted answer, or both. The GPT-4o scaffold includes an "answer-submission" tool and a virtual environment. The scoring function itself was not on the opened pages.
- Inspect's `includes()` scorer, as described on the homepage extract, checks the submitted answer for a flag. Checkpoint scoring is described for inspect_cyber. The cyber docs site was not opened.

## What do they advise builders to copy, as opposed to what a lab did once for a paper?

### Takeaway
Copy the builder documents, not the benchmark papers. Conductor, Arize, Microsoft Learn, LangSmith, and Kohl et al. tell a builder to assert tool, argument, guardrail, and side-effect facts in CI, to script or replay the model when the test must be stable, and to pin and calibrate a judge rather than block on an uncalibrated one. Meta, METR, Harness-Bench, and Zhong and Zhu report how a lab compared agents or harnesses on a suite. Those are study designs. The opened papers do not say a product team should reproduce the suite as its regression harness.

### Cited Findings
- Recommendation aimed at builders, Conductor: the page is written as "Run evals before promoting a new agent version, the same way you run tests before shipping code." It specifies the order: deterministic routing and side effects first, semantic judge second, "run it separately from fast CI when appropriate." It specifies the case inventory for write tools, the scripted runner, replay, pytest fixtures, and a five-layer ladder with layers 1–3 as release blockers for safety or routing. This is advice, not a report of a measured deployment. — [Conductor agent evals](https://conductor-oss.github.io/conductor/devguide/ai/agent-evals.html)
- Recommendation aimed at builders, Arize: deterministic code for schema, permissions, required tools, thresholds, and transaction status; model judges only for open-ended qualities, and only after calibration "when their scores control alerts or deployment gates"; human review for rubric creation, low-confidence scores, evaluator disagreement, and permission-policy changes. The refund-span example is the concrete pattern: do not score the claim, score the side-effect span. — [Arize](https://arize.com/resources/agent-harness-evaluation-tracing/)
- Recommendation aimed at builders, Microsoft Learn: use `LocalEvaluator` tool checks for "CI smoke tests"; call `raise_for_status()` when a failed item should fail the run; set `num_repetitions` when non-determinism matters; for Foundry, pin "datasets, model deployments, evaluator versions, and rubric versions" and "fail CI when required metrics regress." The harness page itself tells the reader how to compose the runtime, not how to test it. The evaluation pages are the testing guidance. — [Microsoft agent evaluation](https://learn.microsoft.com/en-us/agent-framework/agents/evaluation); [Microsoft Foundry evaluation](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/evaluation/microsoft-foundry)
- Recommendation aimed at builders, LangSmith: use trajectory match "when you have specific expectations about which tools should be called and in what order"; use the LLM judge "when you want to evaluate the overall quality and reasonableness of the agent's trajectory without strict tool call or ordering requirements." The CI guide says to run those offline evals in the pipeline that also does unit, integration, and end-to-end tests, and to promote "if All Pass". The guide is an example pipeline "based on the cicd-pipeline-example repository", so it is a documented template, not a claim that LangChain runs this gate on LangChain's own product. That repository was not opened. — [LangSmith trajectory evals](https://docs.langchain.com/langsmith/trajectory-evals); [LangSmith CI/CD example](https://docs.langchain.com/langsmith/cicd-pipeline-example)
- Recommendation with a reported case study, Kohl et al.: they present structural testing as the method to copy: mock the LLM, assert on OpenTelemetry spans, put the pyramid in CI, fail the pipeline on a failed assertion, and use trace-derived tests for regression and test-driven development. They also report that they applied it in case studies, including a customer-data update assertion and a scripted-then-live tire-change conversation, and that "We run the pyramid for each new agent release." The paper does not give pass rates for those case studies in the sections read. — [Kohl et al.](https://arxiv.org/html/2601.18827)
- Recommendation, The Agentic Harness, 2026: block merges on exact match, tool-call correctness, and schema conformance; require pass@k rather than one shot; let a judge block only after human agreement in the stated 0.41–0.60 band, and only on production-trace replays the previous version passed; send the gray zone to a person; feed production failures back into the suite. Treat this as the post's advice. The post does not report that a named organization adopted it, and it does not cite a calibration study for the agreement band in the text read. — [The Agentic Harness](https://theagenticharness.co/posts/building-an-llm-eval-pipeline-in-ci-cd-for-agent-changes)
- Lab practice, not builder instructions, METR 2024: iterate scaffold, prompts, and finetuning on a dev set; freeze that elicitation for the test set; run repeated trials; drop infrastructure errors; read transcripts to separate scaffold bugs from capability gaps; fix "spurious" scaffold failures and do not patch "real" failures at test time. The elicitation page says the procedure had not yet been run as a full evaluation when written, and calls the failure categories "reasoned guesses." The GPT-4o report is one application of the method to 77 tasks, with a manual patch experiment on 10 runs. Copying that patch experiment would be copying a one-off diagnostic, not a regression suite. — [METR elicitation guidelines](https://metr.org/blog/2024-03-15-guidelines-for-capability-elicitation/); [METR GPT-4o report](https://metr.org/evaluations/gpt-4o-report/)
- Lab practice, Meta 2025: build a world whose gold data is a graph of write actions; check tool counts, hard arguments, soft arguments, causality, and timing; keep reads out of the gold trace; unit-test the verifier by perturbing the oracle; compare the verifier to human labels before trusting it; use one ReAct orchestration so model comparisons share a scaffold. Table 1 is a result about the grader, which is the part a builder could copy without copying Gaia2. The 450-trajectory study and the RL hacking anecdote are evidence from that project, not a general threshold. — [ARE paper](https://arxiv.org/html/2509.17158)
- Lab practice, Harness-Bench: compare native harnesses by freezing the task, the sandbox, and the oracle, preserving each harness's own loop, and scoring artifacts with LLM-free module checks and safety gates that zero the score. One run per cell. The paper's claim is that harness choice changes full-credit rate and cost for the same model. It does not tell a team how to regression-test its own harness in CI. The cross-harness numbers (for example GLM-5.3 full-credit gap of 13.5 percentage points, Nanobot at 2.97 times OpenClaw's API cost on GPT-5.6 Sol with a lower full-credit rate) are results of that study. — [Harness-Bench](https://arxiv.org/html/2605.27922v2)
- Proposal, not a completed builder practice, Zhong and Zhu: ablate harness support H0–H3 with model and repository fixed, and judge an episode by whether it produced deterministic verification evidence, failure attribution, and intervention records. They say industrial reports, including Microsoft's, "do not ... specify the evidence that an episode should produce. This paper does." The empirical content they report is one controlled validation task whose episode packages change shape across harness levels. — [Zhong and Zhu](https://arxiv.org/html/2605.13357)
- AISI playbook is framework documentation for people writing capability evaluations, not a product regression guide. What it tells an eval author to copy is the split of sample, solver, and scorer, a sandbox matched to the hazard, explicit budgets, deterministic scorers when phrasing is fixed, model graders when it is not, and logs of every tool call. It does not say to block a software merge on `model_graded_qa`. — [AISI engineering playbook](https://engineering-playbook.aisi.org.uk/evaluate.html)

### Inferences
- The reproducible builder pattern across Conductor, Arize, Microsoft, LangSmith, and Kohl et al. is: a case names the input, the tools that must or must not run, the arguments or side effect that must occur, and a deterministic assertion; a live model is optional and belongs in a slower layer; a judge is pinned and calibrated if it can block anything.
- The lab pattern across METR, Meta, and Harness-Bench is: freeze the scaffold or freeze the task, run the other, score an environment outcome, and spend human review on transcripts or on the verifier. That measures capability or harness effect. It does not, in the opened pages, produce a merge gate for harness code.
- Meta's verifier-versus-human table is the strongest opened evidence that an LLM-only judge of a whole trajectory is the weaker grader. Agreement 0.72 and precision 0.53 against human labels, versus 0.98 and 0.99 for the scripted-plus-soft verifier, using the same Llama 3.3 70B Instruct. That is one benchmark's verifier study, not a universal merge policy.

### Gaps
- No opened source says "copy this harness test suite" as a community standard. Conductor and LangSmith publish APIs and an example pipeline. Kohl et al. publish a method and a GitHub pointer that was not opened.
- Citation counts for the 2026 posts were not measured. The Agentic Harness post is included because it uses the words "agent harness", is dated 2026, and states a CI method. "Widely cited" was not verified.
- Braintrust, productionnotes.dev, longshortlabs, and AgentClash were not opened. They are not used.
- Whether Microsoft's own product CI runs `LocalEvaluator` or Foundry judges on the Agent Framework repository was not checked. The docs describe the APIs and say what they are for.
