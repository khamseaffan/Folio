# OpenAI: evaluating the agent harness, not only the model

Scope: OpenAI primary pages opened through 13 Nov 2026. Dates below are the dates printed on the page. Posts before 2026 are marked older. Claims are split into what OpenAI tells others to do and what OpenAI reports from its own runs. Pages that were not opened are listed under Gaps.

## What does OpenAI say an agent harness or scaffold is, and which part of the system do they evaluate separately from the model?

### Takeaway
OpenAI uses “harness” for the agent loop and the contract around the model (instructions, tools, routing, output rules, validation), and “scaffold” both for that agent environment and for the eval setup used to elicit a capability. Reported scores are for a named model plus a named scaffold, sampling budget, and tool access, not for the base model alone.

### Cited Findings
- Reported definition, Codex harness (23 Jan 2026): “the agent loop, which is the core logic in Codex CLI that is responsible for orchestrating the interaction between the user, the model, and the tools the model invokes.” The same post says this is “the role our agent (or ‘harness’) plays in making use of an LLM,” and that “the Codex harness … provides the core agent loop and execution logic that underlies all Codex experiences.” The loop queries the model, executes a requested tool call, appends the tool output, and repeats until the model emits an assistant message. Codex builds the prompt from `instructions`, `tools`, and `input`. Instructions come from `model_instructions_file` or bundled model-specific instructions such as `gpt-5.2-codex_prompt.md`. Tools include CLI tools, Responses API tools, and user tools, “usually via MCP servers.” — [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Cookbook definition, presented as an example rather than a measured internal result: “the harness is the full contract around the model, including instructions, tools, routing, output requirements, and validation checks.” The same notebook says the Agents SDK prompt, tools, routing rules, output requirements, and validation checks “form the current agent harness,” and that the schema is made explicit “so later optimization can target more than prompt wording.” — [Build an Agent Improvement Loop with Traces, Evals, and Codex](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)
- Advice, platform docs: a trace is “the end-to-end record of model calls, tool calls, guardrails, and handoffs for one run.” Trace grading is for workflow questions (right tool, handoff, policy violation, whether a prompt or routing change improved end-to-end behavior), as distinct from scoring a single model answer. — [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)
- Reported practice, older Codex launch (16 May 2025): “On coding evaluations and internal benchmarks, codex-1 shows strong performance even without AGENTS.md files or custom scaffolding.” They also name a separate product surface: each task runs in an isolated environment, and Codex “can read and edit files, as well as run commands including test harnesses, linters, and type checkers.” The published system message tells the agent that “Only committed code will be evaluated” and that it must run programmatic checks in `AGENTS.md`. — [Introducing Codex](https://openai.com/index/introducing-codex/)
- Reported practice, GPT-5.1-Codex-Max (19 Nov 2025): the footnote says “Terminal-Bench 2.0 ran with Codex CLI in the Laude Institute Harbor harness.” All listed evals “were run with compaction enabled at Extra High reasoning effort.” Compaction is a harness behavior: in Codex applications the model “automatically compacts its session when it approaches its context window limit.” They report an internal observation that the model worked “for more than 24 hours,” iterating on implementation and test failures. The launch post points to a system card for first- and third-party evaluations. That system card was not opened. — [Building more with GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/)
- Reported practice, older deep research system card (25 Feb 2025): “for Preparedness evaluations, we used custom scaffolds to elicit capabilities.” They “modified scaffolds as appropriate to best measure multiple-choice responses versus long-answers versus agentic capabilities.” Production numbers “may vary depending on final parameters, system prompt, and other factors.” Preparedness results are “a lower bound”: “Additional prompting or fine-tuning, longer rollouts, novel interactions, or different forms of scaffolding could elicit behaviors beyond what we observed.” Cyber evals use “a headless Kali Linux distribution with common offensive cybersecurity tools preinstalled as well as a harness which allows the model to call those tools.” SWE-bench is reported in two scaffolds: Agentless 1.0 for models before o3-mini, and “an internal tool scaffold designed for efficient iterative file editing and debugging” for o3-mini, o3-base, and deep research. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); same scaffold split restated on [Deep Research deployment safety hub](https://deploymentsafety.openai.com/deep-research/persuasion)
- Reported practice, older CUA / Operator (23 Jan 2025): CUA is an iterative loop of perception (screenshots), reasoning (chain of thought over screenshots and past actions), and action (click, scroll, type) until completion or a user confirmation. The eval environment is part of the result: WebArena and WebVoyager ran in the Operator browser, not Playwright, because “our model relies on the visual action space” and “does not have access to tool calls that control the navigation.” OSWorld used the authors’ Ubuntu VM with the dock moved to the right, which “improve[d] the performance slightly.” — [Computer-Using Agent](https://openai.com/index/computer-using-agent/); [CUA eval extra information (PDF, Jan 2025)](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)
- Reported engineering use of “scaffold,” not an eval metric (11 Feb 2026): the “initial scaffold” is “repository structure, CI configuration, formatting rules, package manager setup, and application framework,” plus `AGENTS.md`. Humans “validate outcomes” and, when the agent fails, ask “what capability is missing, and how do we make it both legible and enforceable.” Agents also produce “evaluation harnesses.” The post does not publish scores for those harnesses. — [Harness engineering](https://openai.com/index/harness-engineering/)

### Inferences
- When OpenAI reports an agent number, the comparable unit is model plus scaffold plus tool access plus step or try budget. Changing the scaffold is treated as a different measurement, which is why they name Agentless versus the internal tool scaffold, Harbor versus an unnamed SWE setup, and browsing on versus browsing off.
- “Harness” in the Jan 2026 Codex post is the product loop. “Scaffold” in the Feb 2025 system card is the eval-time environment used to elicit a capability. The Feb 2026 harness-engineering post uses “scaffold” for the repo and CI the agent works inside. These are related but not the same object.

### Gaps
- The GPT-5.1-Codex-Max system card linked from the 19 Nov 2025 post was not opened, so any harness settings that live only there are missing.
- The original o3 and o4-mini system card, and the o3 Operator addendum page, were not opened. Search snippets only.
- No OpenAI page opened here gives a formal glossary that distinguishes harness, scaffold, agent loop, and product wrapper in one place.

## Which eval suites, graders, and pass rules do they publish?

### Takeaway
Published agent scoring is mostly outcome tests the agent does not see, plus trace or trajectory checks. Model judges are used for open-ended or changing web tasks, for training rewards, and as a customer-facing grader type. A pass is usually all required tests passing, or a score at or above a stated threshold, not a judgment of wording.

### Cited Findings
- Reported outcome rule, SWE-bench family. Older post (13 Aug 2024): the agent sees the issue text and the repo. “The tests are not shown to the agent.” A proposed edit passes only if both `FAIL_TO_PASS` and `PASS_TO_PASS` tests pass. They released SWE-bench Verified, 500 human-screened samples, and a containerized Docker harness. GPT-4o on the best open-source scaffold they tried, Agentless, resolved 33.2% of Verified. They had annotated 1,699 random SWE-bench test samples with 93 Python developers. — [Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)
- Reported pass rule, deep research system card (25 Feb 2025), same benchmark: “Our primary metric is pass@1, because … we do not consider the unit tests as part of the information provided to the model.” Agentless setting: 5 tries to emit a patch. pass@1 is the average of per-instance pass rates among samples that generated a valid non-empty patch. If every attempt fails to emit a valid patch, the instance is incorrect. Internal tool scaffold: average over 4 tries per instance. All of those runs used a fixed subset of n=477 tasks that ran on internal infrastructure. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf)
- Reported later rejection of that suite (23 Feb 2026): they stopped reporting SWE-bench Verified. An audit of a 27.6% subset of tasks models often failed (138 problems) found material test or description issues in 59.4%. Of the audited tasks, 35.5% had “narrow” tests that enforce implementation details, and 18.8% had “wide” tests for behavior not in the problem statement. Pass rule they restate: the model does not see the tests and passes “only if all tests pass after the code change is applied.” They recommend others report SWE-bench Pro instead, and say their own contamination pipeline found some Pro contamination, “but these cases were significantly rarer,” and “no model was able to produce a complete verbatim gold patch.” They say they are “building new, uncontaminated evaluations” and do not name or score them on this page. — [Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- Reported Codex launch numbers, older (16 May 2025): 23 SWE-bench Verified samples “were not runnable on our internal infrastructure” and were excluded. codex-1 was tested at 192k context and medium reasoning effort. “Our internal SWE task benchmark is a curated set of real-world internal SWE tasks at OpenAI.” No pass rate for that internal set is printed on the page. — [Introducing Codex](https://openai.com/index/introducing-codex/)
- Reported Codex-Max table (19 Nov 2025), before the Feb 2026 decision to stop reporting Verified: SWE-bench Verified n=500, GPT-5.1-Codex (high) 73.7%, GPT-5.1-Codex-Max (xhigh) 77.9%. SWE-Lancer IC SWE 66.3% and 79.9%. Terminal-Bench 2.0 52.8% and 58.1%. The page does not define the pass predicate for SWE-Lancer or Terminal-Bench beyond the Harbor footnote for Terminal-Bench. — [Building more with GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/)
- Reported public agent benchmarks, older deep research launch (2 Feb 2025; page also carries a 17 Jul 2025 update and a 10 Feb 2026 update): Humanity’s Last Exam accuracy 26.6% for “OpenAI deep research” “with browsing + python tools,” on “over 3,000” multiple choice and short answer questions. GAIA: pass@1 of 74.29 / 69.06 / 47.6 / 67.36 average across levels 1, 2, 3, and cons@64 of 78.66 / 73.21 / 58.03 / 72.57. They say ground-truth answers for one dataset “were widely leaked online” and that they “blocked several websites or URLs” for a fair evaluation. An internal expert-task evaluation is described only as domain experts rating that the model “automated multiple hours of difficult, manual investigation.” No rubric or pass threshold for that internal set is printed. — [Introducing deep research](https://openai.com/index/introducing-deep-research/)
- Reported training graders, older system card (25 Feb 2025): training tasks range from “objective auto-gradable tasks with ground truth answers” to “open-ended tasks with accompanying rubrics.” “During training, the model responses are graded against the ground truth answers or rubrics using a chain-of-thought model as a grader.” This is a training reward, not a published product regression gate. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf)
- Reported CUA scores, older (23 Jan 2025): OSWorld 38.1% (human 72.4%), WebArena 58.1% (human 78.2%), WebVoyager 87.0%. Sampling: “All results are obtained by pass@1 autoregressive sampling. By default, we use temperature 0.6 and maximum 200 steps.” WebVoyager used “the automatic evaluation protocol using gpt4o.” They removed 35 broken tasks because live sites change. WebArena used per-site prompts that also force an answer format: if the model does not write the required ``Answer:`` form, “you get no reward at all.” WebVoyager was prompted with the benchmark questions and no extra tips. — [Computer-Using Agent](https://openai.com/index/computer-using-agent/); [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)
- Reported Operator safety sets, older (23 Jan 2025), which grade the deployed agent rather than a base chat model: biorisk tooling success rate 1%, with per-task pass counts out of 10 (AlphaFold 2/10, Ebola FASTA 0/10 despite reaching the page 10/10, Twist DNA order 10/10). Autonomy tasks: 10 runs, maximum 400 steps, success rate, plus a rerun “with more detailed prompts.” Operator “does not score more than 10% on all of the main tasks,” which they map to Low under the Preparedness grading criteria. Harmful agentic tasks: refuses 97% on an internal set where the harmful prompt is initial or mid-conversation. Model mistakes: 100 prompts, 13 nuisance errors, 5 of them irreversible or possibly severe. Confirmations: on 607 tasks across 20 risky-action categories, average recall 92% for asking confirmation when needed. Proactive refusals: 94% recall on a synthetic set. Prompt injection: 31 automatically checkable scenarios, susceptibility 23% after mitigations, 62% with none, 47% with prompting only. A separate monitor, not the agent model, scored 99% recall and 90% precision on 77 red-team attempts, and flagged 46 of 13,704 benign screens. — [Operator System Card](https://openai.com/index/operator-system-card/)
- Reported cyber pass rule, deep research card: 16 rollouts per CTF, “pass@12 metric over the best set of rollouts,” compared with Preparedness thresholds. After dropping contaminated trajectories they switch the reported figure to pass@1 “because after filtering … not all challenges had 12 valid solutions remaining.” Post-mitigation deep research without browsing: 82% high-school, 55% collegiate, 47% professional CTFs. With browsing, before the contamination filter: 92%, 91%, 70%. They say that after removing contaminated rollouts, browsing and no-browsing “fall within the margin of error.” — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf)
- Advice, platform grader types (page current as fetched; no publication date printed; the page says graders are being deprecated inside evals and fine-tuning): string check (`eq`, `ne`/`neq`, `like`, `ilike`) returns 0 or 1. Text similarity (`fuzzy_match`, BLEU, GLEU, METEOR, cosine with `text-embedding-3-large`, ROUGE-1 through ROUGE-5 and ROUGE-L) uses a `pass_threshold`. Score-model grader: a separate model returns `{result, steps}` and the grade is truncated to `range`, defaulting to 0 if non-numeric. `pass_threshold` decides pass. The sample template exposes `output_text`, `output_json`, `output_tools` (tool calls), `choices`, and `output_audio`, so a grader can score tool calls separately from prose. Python grader: a `grade(sample, item) -> float` function, 0 on exception or invalid float, 2 minute limit, no network. They say to build a model-grader eval: detailed task prompts, model and human answers, and human grades (example: expert grades should be 1), then check that the judge ranks those answers in the same order. — [Graders](https://developers.openai.com/api/docs/guides/graders)
- Advice, agent trace grading: grade the trace, not only the final message. Dashboard flow is Logs, Traces, create a grader, run it, then “Grade all” with run options “like model, date range, and tool calls.” No numeric pass threshold is specified on this page. — [Trace grading](https://developers.openai.com/api/docs/guides/trace-grading); [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)
- Advice, Codex skill evals (developers blog, no date printed on the fetched page): an eval is “a prompt, a captured run (trace + artifacts), a small set of checks, a score.” Split checks into outcome, process, style, and efficiency. Deterministic checks parse `codex exec --json` JSONL for `command_execution` events (command ran, exit code 0, order) and for files on disk. A second Codex run with `--output-schema` returns `overall_pass`, `score` from 0 to 100, and per-check `pass` plus notes. They say deterministic checks should come “before you add any model-based grading,” and that the schema exists so the harness can score “across many runs.” Prompt set advice: 10 to 20 prompts, including a negative control (`should_trigger=false`). — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)
- Advice, evaluation guide (no date printed): for a single agent, publish separate evals for tool selection and for “data precision” (correct arguments). The worked example asks “does the order agent correctly call the lookup order tool?” separately from whether the reply contains the correct tracking number. Metric-based evals include “function call accuracy” and “executable evals.” LLM-as-judge modes are pairwise, single-answer, and reference-guided. They name `gpt-6-astra` as the starting judge, then “validate agreement against your human labels.” — [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- Cookbook example, not a reported internal score: the realtime Crawl harness “Grades tool-call correctness and tool-call-arg correctness only.” The Run harness grades “the conversation, tool behavior, and final application state against the hidden expected outcome.” Expected outcomes “remain hidden from the assistant.” Graders in the guide’s case study are deterministic tool selection and argument validity, an LLM rubric, and audio checks. — [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide); crawl and run READMEs under the cookbook paths linked from that guide, including [crawl harness](https://github.com/openai/openai-cookbook/tree/main/examples/evals/realtime_evals/crawl_harness) and [run harness](https://github.com/openai/openai-cookbook/blob/main/examples/audio/duplex_voice_agent_evaluation/run_harness/README.md)

### Inferences
- The stable published pass rule for coding agents is hidden executable tests, all of which must pass. Model judges appear where the outcome is a report, a live website, or a qualitative style check, and OpenAI’s own write-ups treat those judges as noisy enough to require human agreement checks or manual review of failures.
- The Nov 2025 Codex-Max blog still prints SWE-bench Verified. The 23 Feb 2026 post says OpenAI has stopped reporting it. Those two pages disagree about whether Verified is a current reporting metric. The later page is the one that states the reporting policy.

### Gaps
- Pass rules and grader prompts for the “internal SWE task benchmark,” the expert-hours deep research eval, and SWE-Lancer are not on the pages opened. SWE-Lancer is named with percentages only.
- The Codex skill-eval blog has no visible date, so it cannot be placed as 2025 or 2026 from the page itself.
- Deprecation timelines for the Graders API are mentioned but the deprecations page was not opened, so the cutoff date is not recorded here.

## Do they run those checks in CI, offline, or only for model releases? What do they say about variance, retries, and a judge deciding a pass?

### Takeaway
What they report about their own frontier agents is offline evaluation during training and a final sweep before launch, plus sampling variance via multiple tries and bootstrap intervals. What they tell builders is to run evals on every prompt, model, and tool change, with deterministic checks as the regression gate and a judge only after it agrees with humans. They do not say their own Codex or Operator product suites are a blocking CI gate.

### Cited Findings
- Reported timing, deep research card (25 Feb 2025): “We performed evaluations throughout model training and development, including a final sweep before model launch.” “The exact performance numbers for the model used in production may vary depending on final parameters, system prompt, and other factors.” — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf)
- Reported variance method, same card: “We compute 95% confidence intervals for pass@1 using the standard bootstrap procedure that resamples model attempts per problem.” “By default, we treat the dataset as fixed and only resample attempts.” They warn this “can underestimate uncertainty for very small datasets” because it captures sampling variance and not problem-level variance, and “can lead to overly tight confidence intervals, especially when a problem’s pass rate is near 0% or 100% with few attempts.” Retries are explicit: 5 patch tries (Agentless), 4 tries (internal tool scaffold), 16 CTF rollouts. They also “reran the tasks with more detailed prompts” in the Operator autonomy eval, which is a second elicitation condition rather than a retry of the same prompt. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); autonomy rerun in [Operator System Card](https://openai.com/index/operator-system-card/)
- Reported judge noise, same card: they report StrongReject as accuracy rather than goodness@0.1 because goodness@0.1 “is also more sensitive to grader noise.” For a biosecurity rubric they used a preview model “as an autograder, validating agreement with a trusted biosecurity expert,” then “made adjustments to the rubric and iterated on the autograder.” For SWE-bench contamination (23 Feb 2026) a judge model labeled how much novel task-specific information appeared, on a scale from “none” to “strong,” and “another judge” checked that the elicitation model had not leaked too much. “Finally, we then manually reviewed the ‘strong’ examples.” The judge here labels contamination in a transcript. It does not decide the SWE-bench pass. The tests do. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); [Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- Reported judge as the task scorer, older CUA (Jan 2025): WebVoyager “automatic evaluation protocol using gpt4o.” They also say live-site drift means “evaluation results can change” and “may not be directly comparable.” No agreement rate between gpt-4o and humans is printed on that PDF. — [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)
- Reported product CI, not an agent-eval gate (11 Feb 2026): in one internal product built by Codex, “Dedicated linters and CI jobs validate that the knowledge base is up to date.” Architecture rules are “enforced mechanically via custom linters and structural tests.” Separately, “The repository operates with minimal blocking merge gates.” “Test flakes are often addressed with follow-up runs rather than blocking progress indefinitely.” Humans “translate user feedback into acceptance criteria, and validate outcomes.” This is reported practice for that repo’s code and docs, not a published statement that agent trajectories are graded in CI before a model release. — [Harness engineering](https://openai.com/index/harness-engineering/)
- Advice, continuous evaluation: step 5 of the eval workflow is “Set up continuous evaluation (CE) to run evals on every change, monitor your app to identify new cases of nondeterminism, and grow the eval set over time.” The worked objective uses “a held-out set of 1000 reference transcripts” with ROUGE-L at least 0.40 and a coherence score of at least 80% using G-Eval. That example is a summarization system, not an agent harness. Judge advice: start with `gpt-6-astra`, validate against human labels, prefer pairwise or pass/fail, control length because of verbosity bias, and add reasoning before the score. “Once the LLM judge … consistently agrees with human annotations, scale up.” — [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- Advice, Codex skill blog: `codex exec` “is designed for automation and CI.” “If you later move this eval suite into CI, the Codex GitHub Action explicitly supports passing `--output-schema` through `codex-args`.” They do not say OpenAI runs this skill suite as a release gate. — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)
- Advice, realtime cookbook: “Regression suite: hard cases you already fixed. Run on every prompt, model, and tool change.” Holdout set: “a subset of the offline test which stays untouched that you run occasionally.” “If test scores climb while holdout stays flat, you are training for the test.” Deterministic graders are “perfect for tight iteration loops and regression gates.” LLM graders cover what rules cannot. The Run harness should “Constrain randomness,” “Mock tools deterministically,” and “Pin and version the simulator prompt.” A simulator failure should be “backfill[ed] … into a deterministic scripted episode.” They also say offline scores can rise while production quality stalls. — [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)
- Advice, grader API: `pass_threshold` on score-model and text-similarity graders is the pass rule. Sampling params include `seed`, `temperature`, `top_p`, and `reasoning_effort`. Non-numeric judge output “default[s] to 0.” They tell readers to test the judge on a ladder of known answers before trusting it. — [Graders](https://developers.openai.com/api/docs/guides/graders)
- Cookbook example of a gate, not an OpenAI production claim: Promptfoo cases “can combine literal assertions with an LLM rubric judge.” “A fully automated pass can propose useful evals quickly, but people should still check whether the evals are accurate … before they become part of the long-term test suite.” “As the eval gate becomes more trusted, the same handoff can support deeper automation.” Default models in that notebook are named `gpt-5.5` for agent, analysis, eval generation, judge, and HALO. — [Agent improvement loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)

### Inferences
- OpenAI’s own frontier write-ups treat variance as something to measure at release time (multiple tries, bootstrap over attempts, contamination filters), not as a CI flake budget. The one place they describe flake handling in CI is the Feb 2026 internal product repo, and there they say flakes often do not block the merge.
- A judge deciding a pass is something they document for customers and for some open-ended or live-web benchmarks. For SWE-bench they explicitly keep the pass on hidden tests and use judges for side analyses (contamination labels, biosecurity rubric agreement).

### Gaps
- No opened page says whether Codex CLI, Codex cloud, or Operator run an agent-eval suite in their own CI on every commit. The skill blog and the evaluation guide recommend that pattern to readers.
- They do not publish a numeric human-agreement bar that a judge must hit before it is allowed to decide a pass, beyond the qualitative “consistently agrees” and the biosecurity “validating agreement” sentence.
- The continuous-evaluation product setting (how CE is scheduled, what fails a build) is named but not specified on the best-practices page.

## What concrete mechanisms do they describe?

### Takeaway
The mechanisms they actually describe are hidden tests, fixed task subsets, trace JSONL, separate tool-name and tool-argument checks, scripted or mocked tool returns in cookbook harnesses, live-site task removal, and human review of traces when an automatic grader is not enough. Scripted tool failures are recommended for multi-turn voice evals. They are not described as part of the Codex, Operator, or deep research release evals that were opened.

### Cited Findings
- Hidden tests and held-out behavior. SWE-bench: “The tests are not shown to the agent.” Deep research card: pass@1 is used because the model must “implement its change without knowing the correct tests ahead of time.” Realtime Run harness: “Expected outcomes, future caller actions, and grading criteria remain hidden from the assistant.” Best-practices page uses a “held-out set” in a summarization example. Realtime guide: a holdout split of the offline set “stays untouched.” — [Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/); [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)
- Trace inspection. Codex skill blog: `codex exec --json` emits JSONL. Checks look at `item.completed` events whose item type is `command_execution`, including status, exit code, and command string. “If a check fails, you can open the JSONL file and see exactly what happened.” Token use is on `turn.completed`. Trace grading docs: inspect one trace, then grade many, and filter runs by model, date range, and tool calls. Realtime guide: “Manual review = listen to real audio + read full traces end-to-end.” Operator card: “When inspecting these failures we observed” OCR and editor errors, and “A manual review of these examples showed that only one truly concerning example remained.” — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills); [Trace grading](https://developers.openai.com/api/docs/guides/trace-grading); [Operator System Card](https://openai.com/index/operator-system-card/)
- Tool-call correctness separated from wording. Platform docs: tool selection evals versus data-precision evals (right tool, right arguments, then whether the user-facing answer is correct). Graders API: `sample.output_tools` is a distinct field from `sample.output_text`. Crawl harness grades only `tool_call_correctness` and `tool_call_arg_correctness`. Codex skill checks grade “did it run `npm install`” separately from a later rubric over code style. CUA WebArena prompt tells the model that prose around the answer gets “no reward,” which is a format gate on the final string, not a grade of the click trajectory. — [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices); [Graders](https://developers.openai.com/api/docs/guides/graders); [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide); [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)
- Scripted or mocked tools. Advice in the realtime guide: for Run, “Mock tools deterministically: Define expected tool output mocks for the scenario and return those exact outputs.” The Crawl/Walk/Run example includes “an injected tool error once” and says the agent should recover. The same guide says to turn VAD off and use fixed chunk sizes so the harness, not the model, controls variance. This is cookbook guidance. It is not described on the Codex, Operator, CUA, or deep research launch pages. — [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)
- Environment controls they report using. CUA: Operator browser instead of Playwright, dock moved, per-site tips, disabled computer tools listed in the OSWorld prompt (`computer.clipboard`, `computer.sync_file`, and related tools “are disabled”). Deep research: browsing on versus off, and “manually tweaked inference-time settings and available tools” for the pre-mitigation no-browse SWE-bench setting only. Cyber: Kali image plus a command harness. Codex launch: internet disabled in the sandbox at launch, and the agent must not finish until terminal commands complete. Codex-Max: compaction on, Harbor harness for Terminal-Bench 2.0. — [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf); [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); [Introducing Codex](https://openai.com/index/introducing-codex/); [Building more with GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/)
- Contamination and broken-task filters, reported. Deep research: block leaked answer URLs, drop CTF trajectories that opened writeups, and report both contaminated and filtered numbers. CUA: drop 35 broken WebVoyager tasks. SWE-bench Verified retirement: public tasks and gold patches showed up in model behavior, including a chain-of-thought that named a Django parameter the issue text did not require. Their probe gave GPT-5 the task id, description, gold patch, and PR tests over 15 turns and let it vary prompts. — [Introducing deep research](https://openai.com/index/introducing-deep-research/); [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf); [Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- Negative controls and process checks, advice. Skill evals: at least one prompt that must not trigger the skill. Efficiency checks: count `command_execution` items “to catch regressions where the agent starts looping.” Optional outcome checks: `npm run build`, curl against `npm run dev`, `git status --porcelain` against an allow list, and a check that the skill still works without extra permissions. — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)

### Inferences
- The mechanism they use when they want a stable agent score is a frozen environment plus a grader that does not share the agent’s wording: unit tests, exact tool name and arguments, or a structured JSON rubric. Trajectory inspection is how they explain a failure, not how they compute SWE-bench pass@1.
- “Inject a tool failure and see if the agent recovers” is written as a builder pattern in the realtime cookbook. It is absent from the release evals opened for Codex, Operator, and deep research.

### Gaps
- No opened OpenAI research or product post describes a library of scripted tool failures for Codex or deep research.
- Memory as its own eval target is not specified. The Codex loop post says prior turns, tool calls, and compaction are in the prompt. It does not describe a memory-store eval. The realtime guide says multi-turn should test whether the agent “hold[s] goals and constraints across turns,” which is conversational state, not a separate memory system.
- Gates inside the product (confirmation, watch mode, prompt-injection monitor) are evaluated in the Operator card, but the card does not say those gates are re-run in CI.

## What do they explicitly advise others to do, versus what they report from their own runs?

### Takeaway
The advice to outside builders is a small deterministic suite, then a structured model rubric, run on every change, with a holdout set and a judge that has been checked against humans. The record of their own runs is launch-time capability evals: hidden tests or benchmark scripts, multiple tries, custom scaffolds, and a model judge only for some open-ended or live-web tasks, followed by human review when the automatic score is ambiguous.

### Cited Findings
- Advice they give builders:
  - Define success before writing the skill. Keep must-pass checks few. Categories: outcome, process, style, efficiency. Ground the first graders in JSONL behavior, then add a schema-constrained rubric. Turn every manual fix into a new prompt row. Negative controls belong in the set. `codex exec` is for CI. — [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)
  - Start from traces while debugging. Move to datasets and eval runs for repeatability. Use Evals “if you need advanced features such as evaluation against external models.” — [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)
  - Run evals on every change. Grade tool choice separately from argument correctness and from the final answer. Prefer pass/fail or pairwise for judges. Validate the judge on human labels before scaling. Use the most capable judge you can, named on the page as `gpt-6-astra`. — [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
  - For voice or multi-turn agents: three data sets (regression, discovery, holdout), deterministic graders as the gate, LLM graders for the rest, mocked tool outputs, pinned simulator prompts, and promotion of a discovered failure into a scripted episode. — [Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)
  - Iterate the judge itself. Human expert grades are the reference. A judge that cannot rank known-good above known-bad is not ready. Balance labels so the judge cannot guess the majority class. — [Graders](https://developers.openai.com/api/docs/guides/graders)
  - Have a person check generated evals before they become a long-term suite. Trust in the gate is what justifies more automation, not the other way around. — [Agent improvement loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)
  - For coding benchmarks, stop reporting SWE-bench Verified. Report SWE-bench Pro until their new uncontaminated evals exist. If a benchmark is built from public crawls, test for contamination. Automated tests should accept functionally correct solutions and reject shortcuts. “Catching these problems took multiple extensive human labeling campaigns.” — [Why we no longer evaluate SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- What they report doing on their own systems:
  - Codex launch (16 May 2025): scored codex-1 with and without custom scaffolding and `AGENTS.md`, on SWE-bench Verified minus 23 unrunnable tasks, plus an unnamed internal SWE task set. The agent’s own instructions say committed code is what gets evaluated, and the agent must run repo checks. Users are told to review terminal logs, test output, and citations. — [Introducing Codex](https://openai.com/index/introducing-codex/)
  - Codex-Max (19 Nov 2025): reported SWE-bench Verified n=500, SWE-Lancer IC SWE, and Terminal-Bench 2.0 in the Harbor harness, compaction on, extra-high reasoning. Internal long tasks observed past 24 hours. They tell developers to review the agent’s work and to keep the sandbox network off because internet access “can introduce prompt-injection risks.” — [Building more with GPT-5.1-Codex-Max](https://openai.com/index/gpt-5-1-codex-max/)
  - Harness engineering (11 Feb 2026): they report enforcing invariants with linters, structural tests, and doc CI, while keeping merge gates light and fixing flakes with follow-up runs. Humans write acceptance criteria and validate outcomes. They do not publish an agent-eval pass rate for that product. — [Harness engineering](https://openai.com/index/harness-engineering/)
  - Deep research (system card 25 Feb 2025, launch post 2 Feb 2025): training reward from a chain-of-thought grader against answers or rubrics. Release metrics are HLE, GAIA pass@1 and cons@64, Preparedness scaffolds, CTF pass@12 then filtered pass@1, and SWE-bench pass@1 under two scaffolds. They state the numbers are a lower bound on capability and can move with the system prompt. — [Deep Research System Card (PDF)](https://cdn.openai.com/deep-research-system-card.pdf); [Introducing deep research](https://openai.com/index/introducing-deep-research/)
  - Operator and CUA (23 Jan 2025): benchmark pass@1 at temperature 0.6 and 200 steps, gpt-4o as the WebVoyager judge, 10-run safety tasks at up to 400 steps, automatic checks for 31 prompt-injection cases, and a separate monitor model with recall and precision on 77 attacks. They also report a manual review that overturned the raw susceptibility reading down to one concerning case. — [Operator System Card](https://openai.com/index/operator-system-card/); [CUA eval extra information](https://cdn.openai.com/cua/CUA_eval_extra_information.pdf)

### Inferences
- The public how-to is stricter about continuous regression and about not trusting a judge than the launch cards are about OpenAI’s own release process. The launch cards show a final sweep, multiple samples, and occasional human review. They do not show a standing CI suite for the harness.
- Where the two conflict, the later primary page wins on reporting policy: Verified scores in the 19 Nov 2025 Codex-Max post are historical relative to the 23 Feb 2026 decision to stop reporting that benchmark.

### Gaps
- Not opened, so not used: the GPT-5.1-Codex-Max system card, the o3 system card, the o3 Operator addendum, the Graders deprecation schedule, and any “practical guide to building agents” PDF.
- Not used because they are not OpenAI primary sources: ResearchRubrics, LoopsBench, third-party Codex eval write-ups, and GitHub harnesses that only mirror the official skill blog.
- No opened page states an internal pass threshold such as “the harness must hold X% before we ship the model.” Preparedness thresholds are cited as the comparison point for CTF pass@12, but the numeric threshold table itself is not in the pages opened.
