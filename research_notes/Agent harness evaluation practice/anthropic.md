# Anthropic agent harness evaluation

Scope: Anthropic primary pages opened through 13 Nov 2026. Older posts are marked. Recommendation is tagged [Advice]. What Anthropic says it did is tagged [Reported]. Secondary summaries were not used.

## What does Anthropic say an agent harness or scaffold is, and which part of the system they evaluate separately from the model?

### Takeaway
By January 2026 Anthropic defines an agent harness, also called a scaffold, as the software around the model, and says an “agent” score is the harness and the model together. They separately name an evaluation harness, which runs tasks, records transcripts, and grades. They do not publish a method that scores the scaffold with the model held fixed as a routine release metric, though several posts change the scaffold or the resource envelope and report the score moving.

### Cited Findings
- [Reported, 9 Jan 2026] “An agent harness (or scaffold) is the system that enables a model to act as an agent: it processes inputs, orchestrates tool calls, and returns results. When we evaluate ‘an agent,’ we’re evaluating the harness and the model working together. For example, Claude Code is a flexible agent harness, and we used its core primitives through the Agent SDK to build our long-running agent harness.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, 9 Jan 2026] They define a different object, the evaluation harness: “the infrastructure that runs evals end-to-end. It provides instructions and tools, runs tasks concurrently, records all the steps, grades outputs, and aggregates results.” A transcript, also called a trace or trajectory, is “the complete record of a trial, including outputs, tool calls, reasoning, intermediate results, and any other interactions,” and for the Anthropic API “the full messages array.” The outcome is “the final state in the environment,” illustrated by a flight booking that is graded by whether a reservation exists in SQL, not by the agent saying it booked the flight. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, 6 Jan 2025, older] “SWE-bench doesn't just evaluate the AI model in isolation, but rather an entire ‘agent’ system. In this context, an ‘agent’ refers to the combination of an AI model and the software scaffolding around it. This scaffolding is responsible for generating the prompts that go into the model, parsing the model's output to take action, and managing the interaction loop where the result of the model's previous action is incorporated into its next prompt. The performance of an agent on SWE-bench can vary significantly based on this scaffolding, even when using the same underlying AI model.” Their scaffold for upgraded Claude 3.5 Sonnet was a prompt, a Bash tool, and a string-replace edit tool. They sampled until the model finished or hit a 200k context length. The same scaffold produced 49% (new 3.5 Sonnet), 33% (old 3.5 Sonnet), and 22% (Claude 3 Opus) on SWE-bench Verified. — [SWE-bench Verified post](https://www.anthropic.com/research/swe-bench-sonnet)
- [Advice, 19 Dec 2024, older] Workflows are “systems where LLMs and tools are orchestrated through predefined code paths.” Agents are “systems where LLMs dynamically direct their own processes and tool usage.” Agents “are typically just LLMs using tools based on environmental feedback in a loop.” Prompt chaining may add “programmatic checks (‘gate’) on any intermediate steps.” They recommend sandboxed testing and guardrails, and say success is “measuring performance and iterating.” Their own examples of agents are a SWE-bench coding agent and a computer-use reference implementation. The page now carries a note that much of the tooling description has changed since December 2024 and points readers to Claude Managed Agents. — [Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- [Reported, 26 Nov 2025] “The Claude Agent SDK is a powerful, general-purpose agent harness” with compaction. Compaction alone did not let Opus 4.5, given only “build a clone of claude.ai,” produce a production-quality app across context windows. Their fix was two prompts on the same harness: an initializer that writes `init.sh`, `claude-progress.txt`, a git commit, and a JSON feature list, and a later coding agent that does one feature per session. Footnote: they are “separate agents in this context only because they have different initial user prompts. The system prompt, set of tools, and overall agent harness was otherwise identical.” — [Effective harnesses](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- [Reported, 24 Mar 2026] A later harness on the Claude Agent SDK split planner, generator, and evaluator. With Opus 4.5, context resets were “essential” because Sonnet 4.5 showed “context anxiety”; Opus 4.5 “largely removed that behavior,” so that harness dropped context resets and used the SDK’s automatic compaction. Opus 4.6 was then used as a reason to remove the sprint construct, on the claim that 4.6 “plans more carefully, sustains agentic tasks for longer,” and has better code review. The author states the principle that “every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing” because they “can quickly go stale as models improve.” — [Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps)
- [Reported, 5 Feb 2026] On Terminal-Bench 2.0 they held “same Claude model, same harness, same task set” and varied only resource configuration. “To quantify the effect of the scaffold” is the sentence they use for that resource sweep. Success rose with headroom. Infra error rate fell from 5.8% at strict 1x enforcement to 0.5% uncapped. From 1x to 3x, success “fluctuate[d] within the margins of noise (p=0.40).” From 3x to uncapped, infra errors fell another 1.6 points while success rose almost 4 points. Uncapped versus 1x was +6 percentage points (p < 0.01). A SWE-bench crossover on 227 problems with 10 samples each, RAM up to 5x, was “only 1.54 percentage points higher at 5x than 1x.” — [Infrastructure noise](https://www.anthropic.com/research/infrastructure-noise)
- [Reported, Opus 4.5 system card] Terminal-Bench 2.0 was run “using the Terminus-2 harness, in the Harbor scaffold.” Low resource limits “introduced flakiness of up to 13%, primarily due to containers OOM’ing.” They “increased resource limits by 2× for every model” before killing pods, which “reduced infra-related errors to <1%.” Opus 4.5 scored 59.27%±1.34% at a 128k thinking budget (1,335 trials) and 57.76%±1.05% at 64k (2,225 trials). A GPT-5.1-Codex-Max figure in their table “uses a different harness (Codex CLI)” and “was not reproducible by us.” — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, Opus 4.6 system card] Terminal-Bench 2.0 again used “the Harbor scaffold” and “the Terminus-2 harness with the default parser,” on GKE `n2-standard-32` in `us-central1`, “guaranteed resource allocation … at 1×” and “a hard preemption ceiling at 3×,” timeouts at 1×. They “published our adapter open source as a contribution to the Harbor project.” The card points at `anthropic.com/engineering/infrastructure-noise` for the rationale. That engineering URL was not opened separately from the research URL above. Opus 4.6 scored 65.4% at max effort, 61.1% at medium effort, 55.1% at low effort. They reproduced GPT-5.2-Codex at 57.5% on Terminus-2 and 64.7% on “OpenAI’s Codex CLI harness (890 trials).” — [Claude Opus 4.6 System Card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)
- [Reported, Opus 4.5 system card, section 2.6] BrowseComp-Plus was used “as an evaluation for judging the performance of various memory and context management tools for our agent harness.” Features compared included context awareness, tool-result clearing (“retained the 3 most recent results per tool with a clearing threshold of 4”), a memory tool plus a new-context tool (200k context, up to 1M tokens across resets), and subagents. One table, with no fetch tool, lists Opus 4.5 at 67.59% with tool-result clearing and 72.89% with clearing plus memory. A later setup added a fetch tool and is described as producing different numbers. Each bar in the accompanying figure “is a single run.” — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, Opus 4.5 system card, section 2.7] On an internal information-retrieval benchmark, “the multi-agent setup was an effective harness.” Opus 4.5 with Haiku 4.5 subagents scored 87.0% versus 74.8% for Opus 4.5 alone (a 12.2 point difference as they state it). Opus 4.5 orchestrating Sonnet 4.5 subagents scored 85.4% versus 66.5% when Sonnet 4.5 was the orchestrator. Opus 4.5 with Opus 4.5 subagents scored 92.3%. Error margins came from “multiple samples per problem (k=3 to k=8).” — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, 9 Jan 2026] “Opus 4.5 initially scored 42% on CORE-Bench” until a researcher found rigid grading, ambiguous specs, and stochastic tasks. “After fixing bugs and using a less constrained scaffold, Opus 4.5’s score jumped to 95%.” They also cite METR tasks whose grading required exceeding a stated score threshold, which “penalized models like Claude for following the instructions.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### Inferences
- Anthropic’s published distinction is between the agent harness (loop, tools, prompts, memory, context handling) and the evaluation harness (runner, isolation, graders). A published agent benchmark score is not a model-only score.
- The places they come closest to evaluating the scaffold apart from the model are: the 2025 SWE-bench post (same scaffold, different models, and the claim that scaffold changes move scores), the Feb 2026 resource sweep (same model and harness, different machine limits), the Opus 4.5 memory and subagent ablations, and the CORE-Bench jump after a less constrained scaffold. Those are experiments, not a standing “scaffold eval” product.
- The Nov 2025 and Mar 2026 harness posts evaluate harness design by whether a long build stays coherent and, in March, by the author’s inspection of a running app. They publish duration and dollar cost for two examples, not a pass rate on a fixed task suite.

### Gaps
- The Claude Managed Agents post and docs, which the updated Dec 2024 page says are the current approach, were not opened.
- The Claude Opus 4.1 announcement was not opened. A search snippet said the Claude 4 family kept the bash plus string-replace scaffold, dropped the planning tool used for Claude 3.7 Sonnet, and scored the full 500 SWE-bench Verified problems. That claim is unverified here.
- No opened page states a numeric protocol whose only independent variable is the harness (prompts, tools, memory, gates) on a fixed model, with a published pass rule, outside the experiments above.
- `anthropic.com/engineering/infrastructure-noise` was not opened as its own URL. The research URL with the same slug was.

## Which eval suites, graders, and pass rules do they publish?

### Takeaway
The published agent suites they actually run are mostly external benchmarks graded on environment state or an official grader: SWE-bench Verified and variants, Terminal-Bench 2.0, OSWorld and OSWorld-Verified, WebArena, τ2-bench, BrowseComp-Plus, plus internal suites whose items are only partly described. Graders they name are deterministic tests, state checks, tool-call checks, transcript metrics, LLM rubrics, and humans. For coding they say the practical default is unit tests plus an LLM rubric. A judge model is a published grader for BrowseComp-Plus and for WebArena’s fuzzy match, not the pass rule for SWE-bench.

### Cited Findings
- [Advice, 9 Jan 2026] Three grader types, each applied to “some portion of either the transcript or the outcome.” Code-based: string match, binary tests including “fail-to-pass, pass-to-pass,” static analysis, outcome verification, “tool calls verification (tools used, parameters),” and transcript analysis (turns, tokens). Model-based: rubric scoring, natural-language assertions, pairwise comparison, reference-based evaluation, multi-judge consensus. Weakness stated: model graders are “non-deterministic” and “require calibration with human graders.” Human: SME review, crowdsourcing, spot checks, A/B tests, inter-annotator agreement. “For each task, scoring can be weighted (combined grader scores must hit a threshold), binary (all graders must pass), or a hybrid.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Advice, 9 Jan 2026] Coding agents: “Deterministic graders are natural.” SWE-bench Verified “grades solutions by running the test suite; a solution passes only if it fixes the failing tests without breaking existing ones.” Terminal-Bench is cited as end-to-end technical tasks, with examples “building a Linux kernel from source or training an ML model.” They say it is “often useful to also grade the transcript,” including “heuristics-based code quality rules” and “model-based graders with clear rubrics” for “how the agent calls tools or interacts with the user.” The YAML example lists `deterministic_tests`, `llm_rubric`, `static_analysis` (`ruff`, `mypy`, `bandit`), `state_check`, and required `tool_calls`, plus tracked transcript and latency metrics. They then say that example “showcases the full range” and that “in practice, coding evaluations typically rely on unit tests for correctness verification and an LLM rubric for assessing overall code quality, with additional graders and metrics added only as needed.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Advice, 9 Jan 2026] Computer use: “Evaluation requires running the agent in a real or sandboxed environment” and “checking whether it achieved the intended outcome.” WebArena uses “URL and page state checks” and “backend state verification” so that an order is confirmed as placed, not merely that a confirmation page appeared. OSWorld uses “evaluation scripts that inspect diverse artifacts after task completion: file system state, application configs, database contents, and UI element properties.” For Claude for Chrome, “we developed evals to check that the agent was selecting the right tool for each context.” No pass rate for that Chrome tool-selection eval is given. Research agents: groundedness, coverage, source quality, exact match when an answer is objective, and an LLM for unsupported claims. Conversational agents: state check, transcript constraints such as a max turn count, and an LLM rubric, often with a second LLM as the user. They say they use a user-simulator “in our alignment auditing agents.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Advice, 9 Jan 2026] Capability evals “should start at a low pass rate.” Regression evals “should have a nearly 100% pass rate.” Saturated capability evals can “graduate” into a regression suite “run continuously.” Partial credit is recommended when a task has multiple components. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, 6 Jan 2025, older] SWE-bench grades “against the real unit tests from the pull request that closed the original GitHub issue.” SWE-bench Verified is the “500 problem subset” reviewed by humans as solvable. The model is told it must not modify tests. Hidden tests mean the model can believe it succeeded when the official tests fail. They also found failed tasks caused by “environment setup issues, or problems with install patches being applied twice.” One illustrated task “worked for 12 steps” and then “the task's tests then ran successfully.” Some tasks took “more than 100 turns.” The post does not state how many trials were averaged to produce the 49% figure. — [SWE-bench Verified post](https://www.anthropic.com/research/swe-bench-sonnet)
- [Reported, Opus 4.5 system card] Default for the capability table: “an average over 5 trials,” 64k thinking budget, interleaved scratchpads, 200k context, default effort high, default sampling (temperature, top_p), with stated exceptions. SWE-bench Verified, Pro, and Multilingual “averaged over 5 trials.” Opus 4.5: SWE-bench Verified 80.60% with 64k thinking and 80.90% with no thinking; SWE-bench Pro 51.60% and 52.0%; Multilingual 76.20% in both rows as printed. SWE-bench Verified is described as OpenAI’s 500 human-verified problems. Multilingual is 300 problems in 9 languages, run with extended thinking off. SWE-bench Pro is Scale AI’s set of 1,865 problems. — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, Opus 4.6 system card] “All Claude Opus 4.6 evaluation results are an average over 5 trials unless otherwise noted,” adaptive thinking, max effort, default temperature and top_p, context “do not ever exceed 1M.” Footnote: “SWE-bench results are averaged over 25 trials.” Opus 4.6: 80.84% SWE-bench Verified and 77.83% Multilingual, “with the thinking blocks included in the sampling results.” A prompt that told the model to use tools “ideally more than 100 times,” write its own tests first, and look for root causes “resulted in a score of 81.4%” on Verified. The card does not say whether 81.4% is also a 25-trial average. — [Claude Opus 4.6 System Card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)
- [Reported, 9 Jan 2026, and in tension with itself] “LLMs have progressed from 40% to >80% on this eval in just one year.” Later: “SWE-Bench Verified scores started at 30% this year, and frontier models are now nearing saturation at >80%.” Both sentences are in the same post. “This year” is not defined. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, model-card addendum extract, older] Upgraded Claude 3.5 Sonnet on OSWorld, screenshot-only inputs, no accessibility tree. Standard 15 steps: 14.9% overall, 95% CI [11.3, 18.5]. With prompt optimization and 50 steps: 22%, 95% CI [17.8, 26.2]. Human success rate cited as 72.36%. Category table at 15 steps: OS 54.2%, Office 7.7%, Daily 16.7%, Professional 24.5%, Workflow 7.9%. At 50 steps the OS category fell to 41.7% while Office rose to 17.9%. The full PDF was not read line by line. The computer-use news post was not opened. Its search snippet states the same 14.9% and 22.0% figures. — [Model card addendum PDF](https://www-cdn.anthropic.com/c7822cdc35ad788ec87e14b3a9d45010f1f86c38.pdf)
- [Reported, Opus 4.5 and 4.6 system cards] OSWorld for Opus 4.5: “default settings with 1080p resolution and 100 steps,” score “(P@1; avg@5) of 66.26%,” 64k thinking, interleaved scratchpads, 200k context, default effort and sampling. Opus 4.6 reports OSWorld-Verified, same 1080p and 100-step cap, “72.7% (first-attempt success rate, averaged over five runs).” The 4.6 card says it updated the name from OSWorld to OSWorld-Verified. — [Opus 4.5](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf); [Opus 4.6](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)
- [Reported, Opus 4.5 system card] WebArena: “All scores use the official WebArena grader.” Claude was “evaluated using the Computer Use API with additional browser tool definitions and no website specific prompt engineering.” Scores are “the average of 5 independent runs.” Pass@k for Opus 4.5: pass@1 65.3%, pass@2 69.5%, pass@3 71.2%, pass@4 72.4%. A later grading note: “Official WebArena functional grader with the base model for the fuzzy_match subgrader changed from GPT-4 to Claude Sonnet 4.5 with a rewritten judge prompt.” — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, Opus 4.5 system card, τ2-bench] Retail 88.9%, Airline original 70.1%, Airline corrected 87.8%, Telecom 98.2% for Opus 4.5. “All above results used Claude Opus 4.1 to simulate the user and included a prompt addendum instructing Claude to better target its known failure modes when using the vanilla prompt.” A Telecom user-prompt addendum was added “to avoid failure modes from the user ending the interaction incorrectly.” They built a corrected Airline set for “task setup and grading issues” including policy loopholes and “submitted [it] to the authors.” The Jan 2026 eval post uses the same episode as an example of a model that “‘failed’ the evaluation as written, but actually came up with a better solution for the user.” Opus 4.6’s card says they omit Airline results because those loopholes “have not yet been incorporated upstream,” and reports Telecom 99.25% and Retail 91.89% averaged over 5 trials. — [Opus 4.5](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf); [Opus 4.6](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf); [Demystifying evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, Opus 4.5 system card] BrowseComp-Plus grading: “Claude Sonnet 4.5 as the grader,” a prompt different from the paper’s, appendix 8.1. Regrading the authors’ GPT-5 transcripts moved GPT-5 from 70.12% to 72.89%. The harness-feature setup uses “three-way classification (match/no match/uncertain).” One methodology line says “each of these are a single run.” — [Claude Opus 4.5 System Card](https://www-cdn.anthropic.com/bf10f64990cfda0ba858290be7b8cc6317685f47.pdf)
- [Reported, 24 Mar 2026] The in-loop evaluator is not an offline suite. One solo-versus-full comparison: solo 20 min and $9, full harness 6 hr and $200, on the prompt “Create a 2D retro game maker…”. A later simplified Opus 4.6 DAW run was “about 4 hours and $124,” with the planner at 4.7 min and $0.46. - [Reported, 9 Jan 2026] Claude Code evals were added after dogfooding, “first for narrow areas like concision and file edits, and then for more complex behaviors like over-engineering.” No suite size, grader type, or pass threshold is published for those. - [Advice, anthropics/skills, date not read from the file] For an agent that changes an environment, the primary grader “should read the end state, not the transcript”: tests pass, the diff applies, expected files exist, nothing off-limits was touched, steps stay in budget, plus a no-op detector when the agent claims success and the workspace is unchanged. “Transcript-graded ‘did it say the right things’ is the weakest signal for agents; use it only for process guardrails (asked before deleting, didn't leak the secret).” A judge is reserved for “taste dimensions.” Pairwise judges should randomize order, allow `tie` or `both_bad`, and treat candidates as untrusted data. Pointwise rubrics should use structured outputs. “Avoid using the exact model-under-test as its own judge.” This file is instructions for people building evals with Claude. It is not a system card. — [build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)

### Inferences
- Outcome graders are what Anthropic both recommends for coding and computer use and what the release cards report for SWE-bench, OSWorld, and WebArena’s functional grader.
- Transcript graders are recommended as a supplement (tool behavior, user interaction, turn caps, token and latency metrics) and as the thing humans read when a score looks wrong. They are not the published pass rule for SWE-bench or OSWorld.
- Model-based graders are a published component of BrowseComp-Plus, WebArena fuzzy match, research and conversational advice, and the March 2026 in-loop design evaluator. They are described as needing human calibration.
- The illustrative YAML in the January 2026 post is explicitly not their practical coding default.

### Gaps
- No published pass rule, item count, or grader spec for the Claude Code concision, file-edit, or over-engineering evals.
- The Jan 2025 SWE-bench 49% figure has no published trial count in the post that was read.
- Whether the Opus 4.6 81.4% prompt-modified SWE-bench number uses 25 trials is not stated in the section that was read.
- Computer-use announcement page and the rest of the 3.5 model-card addendum were not read. OSWorld numbers above come from the extracted computer-use section.
- The Anthropic cookbook notebook `misc/building_evals.ipynb` was not opened. A search snippet describes single-turn code, human, and model grading. It is older and not an agent-harness spec.
- Internal safety evals in the system cards (malicious computer use refusal rates, agentic misalignment, sandbagging graders) were not reviewed as harness-eval methodology beyond the spots cited.

## Do they run those checks in CI, offline, or only for model releases? What do they say about variance, retries, and a judge model deciding a pass?

### Takeaway
They recommend automated evals in CI/CD and on every commit. What they report for themselves is offline development evals, model-release benchmark runs with multiple trials, production monitoring, and A/B tests. They do not say the Claude Code eval suite is a CI gate. Variance is treated as large enough that a few points on an agentic leaderboard can be infrastructure. A judge model decides some research and computer-use fuzzy grades. For coding benchmarks the published pass is still the test suite. They tell others that a case which passes only on a retry should stay a fail unless the user chooses otherwise. That retry rule is in the skills doc, not in a system card.

### Cited Findings
- [Advice, 9 Jan 2026] Automated evals “can be run during development without real users.” In the method table, a listed pro is “Can run on every commit.” “Automated evals are especially useful pre-launch and in CI/CD, running on each agent change and model upgrade as the first line of defense against quality problems.” Production monitoring is post-launch. A/B tests need traffic. “Sample transcripts to read weekly.” Human studies are for calibrating LLM graders and subjective outputs. “At Anthropic, we experimented with various approaches to eval maintenance. What proved most effective was establishing dedicated evals teams to own the core infrastructure, while domain experts and product teams contribute most eval tasks and run the evaluations themselves.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, 9 Jan 2026] Claude Code “started with fast iteration based on feedback from Anthropic employees and external users. Later, we added evals.” Those evals sit “combined with production monitoring, A/B tests, user research, and more.” The post does not say the Claude Code evals run in CI, on every commit, or only at model release. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, system cards] SWE-bench, Terminal-Bench, OSWorld, WebArena, τ2-bench, and BrowseComp-Plus numbers are published in model system cards, so they are at least release-time measurements. The cards do not describe those suites as CI. Opus 4.6 Terminal-Bench: all 89 tasks, 15 times each, 1,335 trials, “spread across 3 batches at different times to reduce temporal variance.” — [Opus 4.6 System Card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)
- [Advice and reported, 9 Jan 2026] “Because model outputs vary between runs, we run multiple trials.” `pass@k` is the chance of at least one success in k trials. `pass^k` is the chance that all k trials succeed. Illustration, not a product result: a 75% per-trial rate and k=3 gives pass^k of about 42%. “In coding, we’re often most interested in the agent finding the solution on the first try—pass@1.” `pass^k` is for products where “users expect reliable behavior every time.” At k=1 the two metrics match. By k=10, “pass@k approaches 100% while pass^k falls to 0%.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported and advice, 5 Feb 2026] “We have observed anecdotally … that pass rates fluctuate with time of day, likely because API latency varies with traffic patterns and incidents. We have not formally quantified this effect.” For public coding evals, “running at multiple times and on multiple days would help average out the noise.” “Naive binomial confidence intervals already span 1-2 percentage points.” Infrastructure effects “stack on top of that.” “Leaderboard differences below 3 percentage points deserve skepticism until the eval configuration is documented and matched.” The moderate-range spread they observed on Terminal-Bench was “just below 2 percentage points.” The extreme spread was 6. They want resource configuration “documented and controlled with the same rigor as prompt format or sampling temperature.” — [Infrastructure noise](https://www.anthropic.com/research/infrastructure-noise)
- [Reported, 9 Jan 2026] Internal eval contamination: “Claude gaining an unfair advantage on some tasks by examining the git history from previous trials.” Shared CPU or memory limits make trials “not independent.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Advice, 9 Jan 2026, on judges] “We recommend choosing deterministic graders where possible, LLM graders where necessary or for additional flexibility, and using human graders judiciously.” “LLM-as-judge graders should be closely calibrated with human experts.” Give the judge a way to return “Unknown.” “Grade each dimension with an isolated LLM-as-judge rather than using one to grade all dimensions.” “Once the system is robust, it’s sufficient to use human review only occasionally.” “We do not take eval scores at face value until someone digs into the details of the eval and reads some transcripts.” A frontier model at “0% pass@100” is “most often a signal of a broken task, not an incapable agent.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, judges that decided a score] BrowseComp-Plus: Sonnet 4.5, three-way match / no match / uncertain, and their prompt changed both Claude and GPT-5 scores (GPT-5 70.12% to 72.89% on the same transcripts). WebArena: official functional grader, fuzzy_match subgrader switched from GPT-4 to Sonnet 4.5 with a rewritten prompt, average of 5 runs. τ2-bench: a second model (Opus 4.1) plays the user, and grading plus task setup were wrong enough that a corrected Airline set moved Opus 4.5 from 70.1% to 87.8%. March 2026 harness: an evaluator model fails a sprint when any criterion is under a hard threshold. That evaluator was tuned until it matched the author’s judgment, and it had previously approved known bugs. — sources in the previous section
- [Reported, Opus 4.6 system card, judge bias] They asked models to score agent transcripts 0 to 10 and told the grader the transcript was from Claude or from another frontier model. The figure is the difference in mean score. The transcripts were actually from a model different from the graders. This is a self-preference measurement, not their SWE-bench pass rule. The figure values were not extracted. — [Claude Opus 4.6 System Card](https://www-cdn.anthropic.com/6a5fa276ac68b9aeb0c8b6af5fa36326e0e166dd/Claude%20Opus%204.6%20System%20Card.pdf)
- [Advice, skills doc] “Explicit case-retry semantics.” “Default to scoring strict per attempt — a case that passed only on retry is a fail unless the user decides otherwise — and count every attempt in cost.” API retries use jittered backoff, a cap, and a recorded retry count. Attempts that die before a scorable output (API error after retries, tool exception, wall-clock ceiling, grader crash, served-model mismatch) go to `errors.jsonl` and “never go in `results.jsonl`,” so plumbing is not scored as a model failure. Truncated `max_tokens` rows are counted and “left out of the means rather than scoring a clipped answer as wrong.” Noise-floor illustration in the skill: “noise floor ~ `1/sqrt(n·reps)` for a pass-rate; 25 cases × 2 reps is about ±14 points.” — [build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)
- [Reported, 6 Jan 2025, older] Tool-level retry inside the agent loop, not an eval retry: if `old_str` is not a unique match, “the replacement will not be performed” and “the model is shown an appropriate error message for it to retry.” — [SWE-bench Verified post](https://www.anthropic.com/research/swe-bench-sonnet)

### Inferences
- “Run on every commit” and “CI/CD” are recommendations in the January 2026 post, attached to automated evals in general. The Claude Code paragraph describes a later addition of evals plus monitoring and A/B tests, without a CI claim.
- Release cards are where the public pass rates live. Trial counts differ by suite: often 5, SWE-bench 25 for Opus 4.6, Terminal-Bench on the order of 15 reps per task, BrowseComp-Plus harness bars described as single runs.
- Two different “retry” ideas appear. The skills doc says an eval case that passes only because it was re-run should not become a pass by default. The SWE-bench scaffold returns a tool error so the same trial can try the edit again. The system cards do not state which of those policies they use for SWE-bench or OSWorld.
- A judge decides a pass in the research and fuzzy-match settings they document. They also document that the judge prompt moves scores by multiple points on the same transcripts, and that self-grading is lenient.

### Gaps
- No opened page says Anthropic’s own agent evals are or are not a merge gate in their CI.
- No opened page states the temperature, the number of scored retries, or the discard rule for infra failures on the Jan 2025 49% SWE-bench run.
- The Opus 4.5 card’s “increase limits by 2× when a failure is about to kill the pod” and the Opus 4.6 card’s fixed 1× guarantee and 3× ceiling are different procedures. How scores moved between those procedures for the same model is not in the sections read, except that the Feb 2026 post argues the procedure changes the measurement.
- Formal quantification of time-of-day variance is explicitly absent. They say they have not measured it.

## What concrete mechanisms do they describe: scripted tool failures, held-out tasks, trace inspection, separation of tool-call correctness from wording?

### Takeaway
Trace inspection and grading the end state rather than the wording are both recommended and described as internal practice. Held-out tasks are reported for internal tool work and advised when hill-climbing. Scripted injection of tool failures, as an eval technique, was not found. What they do describe is deterministic tool errors returned to the model, optional expected-tool checks that they warn against overfitting, and stubbing live tools when a real side effect cannot be replayed safely.

### Cited Findings
- [Reported and advice, trace inspection, 9 Jan 2026] “At Anthropic, we invested in tooling for viewing eval transcripts and we regularly take the time to read them. When a task fails, the transcript tells you whether the agent made a genuine mistake or whether your graders rejected a valid solution.” “Failures should seem fair.” “As a rule, we do not take eval scores at face value until someone digs into the details of the eval and reads some transcripts.” — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, 6 Jan 2025, older] They publish a full thought, action, and observation trace for one SWE-bench task and say scores were understood by “reviewing attempts” and “inspecting failed tasks,” which is how they found environment and double-applied patch bugs. They render traces as THOUGHT, ACTION, and OBSERVATION “even though we don’t constrain the model to a fixed ordering.” — [SWE-bench Verified post](https://www.anthropic.com/research/swe-bench-sonnet)
- [Reported, 11 Sep 2025] “Review the raw transcripts (including tool calls and tool responses) to catch any behavior not explicitly described in the agent’s CoT.” They also read reasoning blocks. “Most of the advice in this post came from repeatedly optimizing our internal tool implementations with Claude Code.” — [Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)
- [Reported, 24 Mar 2026] Harness iteration included reading the evaluator’s logs, comparing them with the author’s judgment, and editing the QA prompt. Sprint contracts were checked by the evaluator walking the criteria in Playwright. One sprint had 27 criteria. — [Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps)
- [Advice, path versus outcome, 9 Jan 2026] “There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. We’ve found this approach too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn’t anticipate. So as not to unnecessarily punish creativity, it’s often better to grade what the agent produced, not the path it took.” Tool-call verification remains in the code-grader menu. The practical coding line is unit tests plus an LLM rubric. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Advice, 11 Sep 2025] “Avoid overly strict verifiers that reject correct responses due to spurious differences like formatting, punctuation, or valid alternative phrasings.” “You can optionally also specify the tools you expect an agent to call … to measure whether or not agents are successful in grasping each tool’s purpose. However, because there might be multiple valid paths … try to avoid overspecifying or overfitting to strategies.” They track tool-call counts, runtime, tokens, and tool errors. “Lots of tool errors for invalid parameters might suggest tools could use clearer descriptions.” When web search launched, “Claude was needlessly appending `2025` to the tool’s `query` parameter,” found in evaluation, and fixed by editing the tool description. — [Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)
- [Advice, skills doc] Programmatic checks should measure “the answer, not the phrasing.” For agents, grade the end state. Transcript checks are for process guardrails only. If live tools cannot be run safely, “stub those tools (optionally replaying canned tool results) and grade the model's tool calls and response text instead of the downstream effect.” — [build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)
- [Reported, held-out, 11 Sep 2025] “We relied on held-out test sets to ensure we did not overfit to our ‘training’ evaluations.” Figure captions, without numbers in the text: “Held-out test set performance of our internal Slack tools” and “Held-out test set performance of our internal Asana tools.” “These test sets revealed that we could extract additional performance improvements even beyond what we achieved with ‘expert’ tool implementations.” Tasks were “created on top of our internal workspace,” not a toy sandbox. Strong tasks “might require multiple tool calls—potentially dozens.” — [Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)
- [Advice, skills doc] If the user will hill-climb, “fifty-plus inputs with a random held-out slice, or fewer inputs with more reps.” Pairwise hill-climbing should freeze the baseline outputs and not regenerate the reference. — [build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)
- [Advice, 9 Jan 2026, balance rather than the phrase held-out] For Claude.ai web search they built both “queries where the model should search” and “queries where it should answer from existing knowledge,” because a one-sided suite produced overtriggering. “As more example problems come up, we continue to add to evals.” They also say to keep a reference solution that passes every grader, and to test the behavior and its absence. The word “held-out” does not appear in that post. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
- [Reported, tool errors as part of the scaffold, not as an injected eval fault, 6 Jan 2025 and 19 Dec 2024] They “error-proof” tools. Relative paths were replaced by a required absolute path after models “mess[ed] up relative file paths.” String replace fires only on exactly one match and otherwise returns an error the model can retry. They “spent more time optimizing our tools than the overall prompt” on the SWE-bench agent. The Dec 2024 appendix calls this poka-yoke: “Change the arguments so that it is harder to make mistakes,” and says to “run many example inputs in our workbench to see what mistakes the model makes.” — [SWE-bench post](https://www.anthropic.com/research/swe-bench-sonnet); [Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- [Advice, 11 Sep 2025] Error strings should “clearly communicate specific and actionable improvements, rather than opaque error codes.” Claude Code “restrict[s] tool responses to 25,000 tokens by default.” Response shape (XML, JSON, or Markdown) and prefix versus suffix namespacing “have non-trivial effects on our tool-use evaluations.” No numeric delta for namespacing is in the text. — [Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents)
- [Reported, 26 Nov 2025] The long-running harness makes the model verify through tools, not through a claim of success. Coding agents are prompted to use browser automation “as a human user would,” via Puppeteer MCP. “Absent explicit prompting, Claude tended to make code changes, and even do testing with unit tests or curl commands … but would fail [to] recognize that the feature didn’t work end-to-end.” The feature list is JSON because “the model is less likely to inappropriately change or overwrite JSON files compared to Markdown.” Agents may change only the `passes` field. They are told it is “unacceptable to remove or edit tests.” Known hole: Claude “can’t see browser-native alert modals through the Puppeteer MCP,” and features that depend on them “tended to be buggier.” — [Effective harnesses](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- [Reported, 9 Jan 2026] “Make your graders resistant to bypasses or hacks.” The τ2-bench policy loophole and the CORE-Bench numeric-format penalty are the concrete cases. — [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### Inferences
- Separation of wording from success is explicit: the outcome is environment state, and string match on the agent’s final message is treated as brittle. Tool-call correctness is allowed as a check and discouraged as a required sequence.
- Held-out sets are a reported control for tool-description hill-climbing on internal Slack and Asana tools. They are not described as part of the SWE-bench or OSWorld release protocol. Those benchmarks are already fixed external sets.
- “Scripted tool failures” as a named eval mechanism (inject a failed tool result and score recovery) does not appear in the pages that were read. The nearby mechanisms are natural tool errors, canned replays when live tools are unsafe, and grading tool errors as a metric that feeds tool-description edits.

### Gaps
- No opened Anthropic page describes an eval that deliberately injects scripted tool failures, fault rates, or chaos into the tool layer and then scores recovery.
- The Slack and Asana held-out charts have no numbers in the article text. None are invented here.
- The tool-evaluation cookbook linked from the September 2025 post was not opened.
- Docs on `docs.anthropic.com` for the Agent SDK, computer-use tool, and Managed Agents were not opened.

## What do they explicitly advise others to do, versus what they report from their own runs?

### Takeaway
The January 2026 eval post and the skills file are mostly advice, with a smaller set of named internal episodes. The system cards, the SWE-bench scaffold post, the infrastructure study, and the two harness posts are reports of runs. The advice is stricter and more general than the run reports: deterministic end-state grades, human-calibrated judges, isolated trials, transcript reading, CI, and pass^k for customer-facing consistency. The run reports show external benchmarks at release, multi-trial averages, judge prompts that move scores, resource policy that moves scores, and long-running harnesses judged by the author and by an in-loop evaluator rather than by a published regression suite.

### Cited Findings
- [Advice, what they tell others] Start with 20 to 50 tasks from real failures. Write tasks two experts would grade the same way, plus a reference solution. Balance positive and negative cases. Isolate trials from a clean environment. Prefer deterministic graders, then LLM graders, then sparse human review. Do not require a specific tool-call path. Allow partial credit. Use pass@k or pass^k according to whether one success or every-trial success matters. Read transcripts. Keep capability suites from saturating and graduate them into near-100% regression suites. Run automated evals in CI/CD on agent changes and model upgrades. Publish both a guaranteed resource allocation and a hard kill threshold, and calibrate the band so the score at the floor and the ceiling stays within noise. For Terminal-Bench 2.0 they offer 3x as the example that cut infra errors from 5.8% to 2.1% (p < 0.001) while the score change stayed within noise (p = 0.40). Treat differences under about 3 points as unresolved until the setup matches. For tools, use a simple `while` loop per task, record tool errors and tokens, keep a held-out set if you hill-climb, and do not fail a correct answer for phrasing. For agents in the skills file, grade end state, keep the model-under-test off the judge seat, and do not convert a retry-only pass into a pass unless someone decides to. Keep the agent simple until a measurement says the extra piece helps. Gates, in the older workflow sense, are programmatic checks between chained LLM steps. — [Demystifying evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents); [Infrastructure noise](https://www.anthropic.com/research/infrastructure-noise); [Writing tools](https://www.anthropic.com/research/writing-tools-for-agents); [build-eval.md](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md); [Building effective agents](https://www.anthropic.com/research/building-effective-agents)
- [Reported, what they say they did] SWE-bench agent: minimal scaffold, two tools, absolute paths, unique string replace, hidden unit tests, SWE-Agent as the code foundation, 49% on Verified for new Claude 3.5 Sonnet in Jan 2025 with no trial count in that post. Later cards: same benchmark family, 5 trials (Opus 4.5) or 25 trials (Opus 4.6), 80.90% and 80.84% on Verified, and a prompt change associated with 81.4%. Terminal-Bench 2.0 on Harbor and Terminus-2, with an evolving resource policy (2× bump on Opus 4.5’s card, 1×/3× on Opus 4.6’s card) and a measured 6 point infra swing. OSWorld screenshot-only 14.9% at 15 steps and 22% at 50 steps for new Claude 3.5 Sonnet, then 66.26% (Opus 4.5, 100 steps, avg@5) and 72.7% on OSWorld-Verified (Opus 4.6, five runs). WebArena official grader, five runs, pass@k published, fuzzy match judged by Sonnet 4.5. τ2-bench with an Opus 4.1 user simulator and a corrected Airline set. BrowseComp-Plus graded by Sonnet 4.5, sometimes a single run, used to compare memory and context tools. Internal multi-agent search with k from 3 to 8. Claude Code evals for concision, file edits, and over-engineering, with no published threshold. Internal web-search trigger evals in both directions. Git history leaked across internal trials until they noticed. CORE-Bench 42% to 95% after grader and scaffold fixes. Long-running harness: initializer plus one-feature sessions, JSON feature list, git and progress files, Puppeteer or Playwright as the verification tool, then a separate skeptical evaluator with hard per-criterion failure. Held-out Slack and Asana tool evals on the real internal workspace. They say they read transcripts with internal tooling and that dedicated evals teams own infrastructure while product teams write tasks and run evals. — the posts and cards cited above
- [Reported versus advice on the same topic] They advise against grading a prescribed tool sequence, and their SWE-bench prompt still suggests a five-step approach while saying the model is “free to choose how it moves from step to step.” They advise pass^k where consistency matters, and the release tables they print are almost all averages, pass@1, or avg@5, with one WebArena pass@k table and no published pass^k for a Claude product. They advise CI on every agent change. The runs they document in public are release benchmarks, internal tool held-outs, and author-run harness experiments. They advise human calibration of judges. The calibration they describe in detail is the March 2026 author retuning an evaluator prompt, Descript’s “periodic human calibration,” and the general claim that Anthropic reads transcripts. They do not publish inter-annotator agreement for the Sonnet 4.5 BrowseComp or WebArena judges.

### Inferences
- A reader who copies only the system-card protocol will run an external benchmark many times on a pinned scaffold and a pinned machine, and will let unit tests or an official environment script decide the pass. A reader who copies only the January 2026 essay will also build small internal suites, read traces, mix an LLM rubric, track regression near 100%, and wire the suite to CI. Anthropic describes both, and it documents the first more quantitatively than the second.
- The harness posts are reports of a design that worked on a few app builds. They are not a report that this harness was scored on a frozen eval before the design was kept, except for the qualitative solo-versus-full comparison and the author’s log review.
